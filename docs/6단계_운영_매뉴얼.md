### 2.5 백엔드 없이 사용하기

백엔드를 띄우지 않아도 앱은 동작합니다. 다음 기능만 비활성화됩니다.

| 기능 | 백엔드 없이 |
| --- | --- |
| 전술 편집, 국면 전환, 공간 레이어 | ✅ 사용 가능 |
| PNG 카드 내보내기 | ✅ 사용 가능 |
| JSON 내보내기 / 가져오기 | ✅ 사용 가능 |
| 분석 저장 / 목록 조회 / 삭제 | ❌ 비활성화 |

즉 저장만 안 될 뿐이므로, 급할 때는 백엔드 없이 작업하고 **JSON 내보내기로 결과를 보관**하면 됩니다. (백엔드를 실제로 내려놓고 편집·드래그·PNG 다운로드·JSON 내보내기가 모두 동작하는지, 저장 버튼이 비활성화되고 안내 문구가 뜨는지 확인했습니다.)

### 2.6 운영자 계정 지정 (ADMIN_EMAILS, 2026-09-20 개선 로드맵 §5.5 신설)

신고 처리 화면(`/admin/reports`, "신고함" 메뉴)과 운영자 전용 API(`GET /api/moderation/reports` 등)는 `ADMIN_EMAILS` 환경변수(콤마 구분 이메일 목록)로만 접근을 허용합니다. **이 값을 설정하지 않으면 어떤 계정도 운영자가 아니게 되어 신고 처리 기능 자체를 아무도 쓸 수 없습니다** — DB에 별도 플래그가 없어서, 가입 순서나 UI만으로는 운영자를 지정할 방법이 없습니다.

- **로컬 개발**: `backend/.env`에 `ADMIN_EMAILS=본인이메일@example.com`을 추가하고 백엔드를 재시작합니다. 여러 명이면 콤마로 구분합니다(`a@x.com,b@x.com`).
- **Fly.io 배포**: `COOKIE_SECURE`(`fly.toml`의 `[env]`)와 달리 이 값은 실제 이메일 주소가 담기므로 `fly.toml`에 평문으로 커밋하지 말고 `flyctl secrets set ADMIN_EMAILS=본인이메일@example.com`으로 설정합니다. Fly 시크릿을 바꾸면 머신이 재기동됩니다.

설정 후 그 이메일로 로그인하면 `/api/auth/me` 응답에 `is_admin: true`가 실리고, 헤더 내비에 "신고함" 링크가 나타납니다.

## 3. 데이터 관리

### 3.1 DB 파일 위치

```
data/tacticore.db   (저장소 루트 기준 — backend/ 아래가 아니다)
```

> **정정 (2026-09-01).** 이 문서의 이전 버전은 `backend/tacticore.db`라고 적었으나, 실제 `backend/config.py`의 `DEFAULT_DB_PATH`는 프로젝트 루트의 `data/`를 가리키도록 배포 단계에서 의도적으로 바뀌었습니다(CLAUDE.md의 Docker 관련 결정 참조 — 컨테이너의 `/app/data` 바인드 마운트와 로컬 실행이 같은 상대 경로를 쓰게 하기 위함). `backend/.env`에서 `DATABASE_URL`을 직접 지정하지 않는 한 이 경로가 적용됩니다.

SQLite 단일 파일입니다. Git에 커밋되지 않도록 `.gitignore`에 등록되어 있습니다(§7-9, `data/` 전체가 무시 대상).

### 3.2 백업 (2026-09-20 갱신, 개선 로드맵 §5.4)

> **이전 버전 정정**: 예전 이 절은 "서버를 종료한 뒤 `Copy-Item`으로 복사"를 권했습니다 — 서버가 켜진 채로 파일을 그냥 복사하면 쓰기 도중의 상태가 찍힐 수 있어서였습니다. 지금은 그 문제 자체를 피하는 스크립트가 있어 **서버를 켠 채로도 안전하게 백업할 수 있습니다.**

```powershell
.\scripts\backup-db.ps1
```

`scripts/backup_db.py`가 `sqlite3.Connection.backup()`(SQLite 자체의 온라인 백업 API)으로 `data\backups\tacticore_<타임스탬프>.db`에 일관된 스냅샷을 만듭니다 — 서버가 쓰기 중이어도 반쪽짜리 상태가 찍히지 않습니다. 기본으로 최근 14개(매일 한 번 돌린다고 가정하면 2주치)만 남기고 오래된 것부터 자동 삭제합니다(`--keep <N>`으로 조절). `data/` 전체가 `.gitignore` 대상이라 `data/backups/`도 커밋되지 않습니다.

**실제로 검증했습니다** (2026-09-20) — 백업을 만든 뒤 `PRAGMA integrity_check`가 `ok`를 반환하고, `analyses`·`users`·`players`·`comments` 테이블의 행 수가 원본과 정확히 일치하며, 백업 파일을 별도 경로로 복사해 다시 열어도 정상 조회되는 것까지 확인했습니다(아래 §3.6 복구 절차와 같은 방식) — "백업 파일이 실제로 복원 가능한지"까지 리허설한 결과입니다.

**정기 실행**: 이 스크립트를 크론/작업 스케줄러에 등록하는 자동화는 아직 없습니다 — 지금은 수동 실행입니다. 자동화가 필요해지면 Windows 작업 스케줄러(`schtasks`)에 매일 1회 `backup-db.ps1` 실행을 등록하세요.

### 3.5 스키마 변경 시 (2026-09-20 정정)

> **이전 버전 정정**: 이 절은 원래 "JSON으로 내보내기 → DB 삭제 → 재기동 → JSON 가져오기"를 권했습니다. 그 절차가 의존하는 **JSON 내보내기/가져오기 기능 자체가 2026-09-11(TO-DO 32번)에 제거됐습니다** — 저장/공유/PNG로 충분하다는 판단이었습니다(CLAUDE.md "현재 상태" 참조). 아래 §4 전체도 지금은 존재하지 않는 기능을 설명하고 있으니 실행하지 마세요.

MVP는 여전히 Alembic 같은 정식 마이그레이션 도구를 쓰지 않지만, 실제로는 **DB를 지우고 재생성하는 절차 자체를 거의 쓰지 않습니다** — TO-DO 20번(2026-09-07, `players.tactical_role`) 이후 모든 스키마 변경은 `backend/main.py`의 `_ensure_column()`/`_backfill_*()` 패턴으로 처리합니다. 서버가 기동할 때마다 필요한 컬럼·인덱스·기본값을 스스로 점검해 없으면 추가하는 방식이라(재실행해도 안전 — 있으면 아무것도 안 함), **기존 데이터를 지우지 않고도 스키마가 자동으로 최신화됩니다.** 최근 예: `analyses.visibility`/`share_token`(개선 로드맵 §5.2), `comments.parent_id`, `users.username`. 새 컬럼 추가 절차:

1. `models.py`에 컬럼 추가
2. `main.py`에 `_ensure_column("테이블", "컬럼", "SQLite 타입")` 한 줄 추가
3. 기존 행에 채워 넣을 초기값이 필요하면 `_backfill_*()` 함수 추가(예시: `_backfill_usernames`, `_backfill_visibility_and_tokens`)
4. 서버 재기동 — 자동 적용됨

**컬럼 삭제·타입 변경처럼 `ALTER TABLE ADD COLUMN`으로 안 되는 변경**(SQLite는 컬럼 삭제·이름 변경 지원이 제한적)만 여전히 예외적으로 수동 개입이 필요합니다 — 그런 경우 §3.6 복구 절차로 만든 백업을 안전망 삼아 진행하세요.

### 3.6 복구(재해복구) 절차 (개선 로드맵 §5.4, 2026-09-20 신설)

`data/tacticore.db`가 손상되었거나 실수로 지워졌을 때 §3.2에서 만든 백업으로 되돌리는 절차입니다.

```powershell
# 1. 서버가 켜져 있으면 먼저 내립니다(Ctrl+C) — 복구 중 쓰기가 섞이면 안 됨
# 2. 현재 파일이 남아 있다면(완전 삭제가 아니라 손상만 의심되는 경우) 조사용으로 먼저 옆으로 치웁니다
Move-Item data\tacticore.db data\tacticore.db.broken -ErrorAction SilentlyContinue

# 3. 복구할 백업을 고릅니다 — 최신순 정렬
Get-ChildItem data\backups\tacticore_*.db | Sort-Object LastWriteTime -Descending | Select-Object -First 5

# 4. 고른 백업을 실제 DB 경로로 복사
Copy-Item data\backups\tacticore_<타임스탬프>.db data\tacticore.db

# 5. 정합성 확인 후 서버 기동
.\backend\.venv\Scripts\python.exe -c "import sqlite3; print(sqlite3.connect('data/tacticore.db').execute('PRAGMA integrity_check').fetchone())"
uvicorn main:app --reload --port 8000
```

정합성 확인(4단계)에서 `('ok',)`가 아니라 다른 값이 나오면 그 백업도 손상됐을 수 있습니다 — 더 오래된 백업으로 다시 시도하세요. **복구는 그 백업 시점 이후의 데이터(그사이 저장된 분석)를 잃습니다** — 백업 주기(기본 매일 수동 실행)가 곧 최대 손실 범위라는 뜻이므로, 자주 저장하는 시기엔 백업도 자주 돌리세요.

이 절차는 2026-09-20에 로컬 DB로 실제 리허설을 완료했습니다(백업 생성 → `PRAGMA integrity_check` → 다른 경로에 복사해 재조회 → 테이블별 행 수가 원본과 정확히 일치함을 확인) — 문서만 쓰고 안 돌려본 절차가 아닙니다.

### 3.7 Fly.io 배포본(프로덕션) 백업·복구

로컬 백업 스크립트(`backup-db.ps1`)는 로컬 `data/tacticore.db`만 다룹니다. 배포본(https://tacticraft.fly.dev)의 DB는 Fly.io 볼륨(`data`, `/app/data/tacticore.db`)에 있어 별도 절차가 필요합니다 — **이 절차는 실제 운영 데이터에 접근하므로 세션이 사용자 대신 자동 실행하지 않습니다.** 필요할 때 사용자가 직접 실행하세요([[deployment-flyio]] 메모의 `flyctl` PATH 설정 참고).

```powershell
# 배포본 DB를 로컬로 내려받기(읽기 전용 — 배포본은 건드리지 않음)
flyctl ssh sftp get /app/data/tacticore.db data\backups\tacticore_fly_$(Get-Date -Format 'yyyyMMdd_HHmmss').db -a tacticraft

# 내려받은 파일 정합성 확인
.\backend\.venv\Scripts\python.exe -c "import sqlite3; print(sqlite3.connect('data/backups/tacticore_fly_<타임스탬프>.db').execute('PRAGMA integrity_check').fetchone())"
```

복구(배포본에 로컬 백업을 다시 올리는 것)는 실제 서비스 중단·데이터 덮어쓰기를 동반하는 훨씬 위험한 작업이라 이 문서만으로 실행하지 마세요 — 필요해지면 그 시점에 `flyctl ssh sftp shell`이나 볼륨 교체 절차를 별도로 검토하고, 반드시 위 백업부터 새로 받아 둔 뒤 진행하세요.

## 4. (기능 제거됨) JSON 입출력 가이드

> **2026-09-11 이 기능 자체가 제거됐습니다(TO-DO 32번)** — 아래 §4.1~4.3은 더 이상 앱에 존재하지 않는 "JSON 내보내기/가져오기" 버튼을 설명합니다. 저장(DB)·공유 링크·PNG 내보내기로 충분하다는 판단이었습니다. 데이터 백업·이관·복구는 §3.2~3.7을 참조하세요. 이 절은 과거 기록으로만 남겨 둡니다.

DB와 별개로, 분석 1건을 파일로 주고받는 수단입니다.

### 4.1 내보내기

편집 화면에서 `JSON 내보내기` → `.json` 파일이 다운로드 폴더에 저장됩니다. 이 파일은 백업, 다른 PC로의 이동, 스키마 변경 시 재적재에 모두 쓸 수 있습니다.

### 4.2 가져오기

`JSON 가져오기`에서 파일을 선택합니다. 형식이 어긋나면 어느 위치가 잘못됐는지 안내가 표시됩니다. 자주 나오는 오류:

| 오류 | 원인 | 조치 |
| --- | --- | --- |
| 좌표 범위 초과 | `x` 또는 `y`가 0~100을 벗어남 | 값을 백분율로 수정 |
| 선수 수 불일치 | `players`가 11명이 아님 | 11명으로 맞춤 |
| 상대팀 좌표 개수 오류 | `opponentPositions`가 있는데 11개가 아님 | 11개로 맞추거나 항목 전체를 삭제 |
| 국면 누락 | `base`/`attack`/`defense` 중 빠짐 | 세 국면 모두 포함 |
| 날짜 형식 | `matchDate`가 `YYYY-MM-DD`가 아님 | 형식 수정 |

### 4.3 샘플 파일

`frontend/public/samples/sample-4-3-3.json`에 샘플 경기 JSON이 있습니다. 처음 사용할 때 이 파일을 "JSON 가져오기"로 불러와 구조를 확인하세요. 국면 3개 모두 좌표·상대팀 좌표·코멘트가 채워져 있어 오버로드 레이어까지 바로 확인할 수 있습니다. (실제로 가져오기해서 검증 오류 없이 로드되는지 확인했습니다.)

## 5. 데이터 입력 가이드

### 5.1 좌표 규칙

- 모든 좌표는 **0~100 백분율**입니다. 미터나 픽셀이 아닙니다.
- `y = 0`이 상대 골라인, `y = 100`이 자팀 골라인입니다. **값이 작을수록 전진한 위치**입니다.
- `x = 0`이 왼쪽 터치라인, `x = 100`이 오른쪽 터치라인입니다.
- 환산 기준은 105m × 68m입니다. `y` 1% ≈ 1.05m, `x` 1% ≈ 0.68m.

### 5.2 채널 경계

| 채널 | x 범위 |
| --- | --- |
| 좌측 측면 | 0 ~ 20 |
| 좌측 하프스페이스 | 20 ~ 36.5 |
| 중앙 | 36.5 ~ 63.5 |
| 우측 하프스페이스 | 63.5 ~ 80 |
| 우측 측면 | 80 ~ 100 |

수직 3분할: 공격 서드 `0~33.3`, 중원 `33.3~66.7`, 수비 서드 `66.7~100`.

### 5.3 오버로드 레이어를 쓰려면

상대팀 11명의 좌표를 입력해야 활성화됩니다. 입력하지 않으면 토글이 비활성 상태로 표시됩니다. 부분 입력(예: 5명만)은 허용되지 않습니다 — 11명 전부이거나, 전부 없거나입니다.

수적 우위 판정 기준:

| 자팀 − 상대 | 표시 |
| --- | --- |
| 2명 이상 많음 | 진한 하이라이트 |
| 1명 많음 | 옅은 하이라이트 |
| 같거나 적음 | 표시 없음 |

### 5.4 GK 판별

앱은 역할(`role`) 문자열이 아니라 **y값이 가장 큰 선수 1명을 GK로 간주**합니다. 압박 라인 자동 산출과 콤팩트니스 계산에서 이 선수를 제외합니다. 따라서 GK를 필드 중앙까지 끌어올려 배치하면 계산이 틀어질 수 있습니다.

### 5.5 권장 작성 순서

1. `/new`에서 포메이션 프리셋 선택 → 11명 자동 배치
2. 선수 이름·등번호 입력
3. `기본` 국면에서 드래그로 실제 배치 조정
4. `공격` 국면으로 전환 → 해당 국면 대형으로 드래그
5. `수비` 국면 동일하게 조정
6. 국면별 코멘트 + 종합 평가 입력
7. 저장(DB) 또는 JSON 내보내기
8. PNG 카드 내보내기

## 6. 문제 해결

### 6.1 포트가 이미 사용 중

```powershell
# 8000 포트를 쓰는 프로세스 확인
Get-NetTCPConnection -LocalPort 8000 -State Listen | Select-Object OwningProcess
Get-Process -Id <PID>
```

다른 포트로 띄우려면 백엔드는 `--port 8001`, 프론트는 `npm run dev -- --port 5174`. 포트를 바꾸면 `frontend/.env`의 `VITE_API_BASE_URL`과 `backend/.env`의 `CORS_ORIGINS`도 함께 고쳐야 합니다.

### 6.2 저장 버튼이 비활성화됨

백엔드가 실행 중이 아닙니다. `http://localhost:8000/api/health`에 접속해 `{"status":"ok"}`가 나오는지 확인하세요.

### 6.3 CORS 오류

브라우저 콘솔에 `blocked by CORS policy`가 뜨면, 프론트 주소가 `backend/.env`의 `CORS_ORIGINS`에 없는 경우입니다. 포트를 바꿨거나 `127.0.0.1`로 접속한 경우 발생합니다 — `localhost`와 `127.0.0.1`은 다른 오리진으로 취급됩니다.

### 6.4 삭제해도 데이터가 남음

`PRAGMA foreign_keys=ON`이 적용되지 않아 CASCADE가 동작하지 않는 경우입니다. `database.py`의 이벤트 리스너를 확인하세요(4단계 §2.1).

### 6.5 국면 전환 시 선수들이 서로 자리를 바꿈

Framer Motion의 노드 key가 `player.id`가 아니라 배열 인덱스로 되어 있습니다. 4단계 §5.1 참조.

### 6.6 PNG 카드의 글꼴이 다르게 나옴

`document.fonts.ready`를 기다리지 않고 캡처한 경우입니다. 4단계 §5.3 참조.

### 6.7 PNG 카드가 빈 이미지로 나옴

두 가지 원인이 있을 수 있습니다.

1. 캡처 대상 노드를 `display:none`이나 `visibility:hidden`으로 숨긴 경우입니다. `position:absolute; left:-9999px`를 써야 합니다.
2. **(구현 중 실제로 겪은 원인)** `position:absolute; left:-9999px`를 캡처 **대상 노드 자신**에 걸어도 빈 이미지가 나올 수 있습니다. html-to-image가 노드를 복제해 SVG로 직렬화할 때 그 오프셋이 그대로 다시 적용되어 콘텐츠가 캡처 영역 밖으로 밀려나기 때문입니다. 화면 밖 배치는 **바깥쪽 래퍼**에만 걸고, 캡처에 넘기는 ref는 오프셋이 없는 **안쪽 카드 노드**를 가리켜야 합니다 (`ShareCard.tsx` 참조, 5단계 §9에 기록).

### 6.8 WSL에서 vite가 `Cannot find module @rollup/rollup-linux-x64-gnu`로 죽음 (또는 Windows에서 반대)

이 저장소를 Windows와 WSL 양쪽에서 같은 `frontend/node_modules`로 개발할 때 생깁니다. `npm install`은 **실행한 OS의 플랫폼바이너만 남기고 반대편을 가지치기**합니다. 어느 한쪽 OS에서 install을 돌리면 반대쪽 OS의 vite가 깨집니다.

복구 방법 (현재 OS 기준):

```bash
npm install --no-save @rollup/rollup-linux-x64-gnu @esbuild/linux-x64
```

단 이 명령은 반대 OS(Windows)의 바이너리를 지웁니다. **양쪽을 동시에 살리려면** 반대편 바이너리를 수동으로 심습니다:

```bash
cd frontend
npm pack @rollup/rollup-win32-x64-msvc@<rollup 버전> @esbuild/win32-x64@<esbuild 버전>
tar -xf rollup-rollup-win32-x64-msvc-*.tgz -C node_modules/@rollup/rollup-win32-x64-msvc --strip-components=1
tar -xf esbuild-win32-x64-*.tgz -C node_modules/@esbuild/win32-x64 --strip-components=1
```

`npm install`을 실행할 때마다 반대편이 다시 지워지므로, **한 OS에서만 install을 돌리고 다른 OS에서는 위 복구 절차**를 쓰는 게 안전합니다. (WSL + Windows 개발 환경에서 2026-09-01 실제로 겪은 사례 — 5단계 §10 참조)

### 6.9 로그 확인

FastAPI 기본 로그가 백엔드 터미널에 출력됩니다. 별도 로그 파일은 MVP에서 만들지 않습니다.

```powershell
# 요청 로그를 파일로도 남기려면
uvicorn main:app --reload --port 8000 --log-config logging.json
```
