### 33. GIF 내보내기가 끝없이 "만드는 중"에 멈추는 버그 수정

- **내용**: "gif내보내기 했는데 계속 만드는 중 이야" 리포트. Playwright로 그대로 재현 — 버튼이 "GIF 만드는 중…"에서 30초 넘게 안 바뀌었다(이전 세션과 달리 이번엔 데스크톱 Chromium에서도 100% 재현되는 버그였다).
- **원인**: 콘솔에 프레임마다 반복되는 에러 쌍을 확인했다 — `html-to-image`의 `toCanvas`가 캡처할 때마다 `embedWebFonts` 단계에서 문서의 모든 스타일시트의 `cssRules`를 읽으려 시도하는데, `index.html`에 Hallmark 리디자인(2026-09-11, 29번 항목) 때 추가한 Google Fonts `<link rel="stylesheet" href="https://fonts.googleapis.com/...">`가 **cross-origin**이라 `cssRules` 접근 자체가 브라우저 CORS 정책으로 막혀 `SecurityError: Failed to read the 'cssRules' property`가 매번 발생했다. GIF는 39프레임(`buildGifFrameSpecs`: 국면 3개 × (정지 1장 + 전환 보간 12장))을 순서대로 캡처하는데, 이 실패한 시도 하나가 프레임당 약 2초를 잡아먹어 **39장 전체가 70초 넘게 걸렸다** — "끝없이 멈춘" 게 아니라 극도로 느려진 것. PNG 내보내기(1회 캡처)는 같은 에러를 조용히 한 번만 겪고 넘어가서 눈에 안 띄었을 뿐 똑같이 느려지고 있었다.
- **수정**: `html-to-image`의 `toCanvas`/`toPng` 호출 3곳(`GifExportRunner.tsx`, `lib/exportImage.ts`의 `exportCard`·`captureThumbnail`) 전부에 `skipFonts: true` 옵션 추가 — 캡처는 이미 `document.fonts.ready`로 폰트가 로드·페인트된 같은 브라우저 탭 안에서 일어나므로, html-to-image가 폰트를 별도로 재다운로드해 SVG에 base64로 embed할 필요가 없다(embed는 SVG 마크업을 이 탭 밖에서 독립적으로 쓸 때만 의미가 있음). 이 단계를 건너뛰면 CORS 에러 자체가 안 나고, 시각적 결과물(이미 렌더링된 폰트 그대로 캡처)도 동일하다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(174, 회귀 없음)/`npm run build` 통과. Playwright로 GIF 내보내기 재현 — 수정 전 30초 관찰 동안 한 번도 안 끝나던 게, 수정 후 **4초 만에** 버튼이 "GIF 내보내기"로 돌아오고 다운로드가 트리거됨을 확인, 콘솔에 CORS `SecurityError`가 더 이상 안 뜨는 것도 확인.
- **추가 확인**: Playwright로 실제 다운로드된 GIF 파일을 저장해 육안으로 열어봄 — 제목이 Nanum Gothic Coding, 본문이 IBM Plex Sans KR로 정상 렌더링되고 폰트 폴백으로 인한 간격 깨짐(이전 세션에서 잡았던 버그) 없이 나온 것을 확인. GIF 전체 재생(프레임 간 애니메이션)까지는 정적 이미지 뷰어로 확인이 안 돼 이 부분만 사용자 확인이 남는다.
- **미확인**: 여러 프레임에 걸친 실제 재생(모프 애니메이션이 자연스럽게 이어지는지)은 GIF를 재생 가능한 뷰어로 열어야 확인되므로 사용자가 봐줘야 한다.

### 34. 프리셋 선수 이름 한국어 표기 전수 조사·수정 + 피치 선수 이름 폰트 명시

- **내용**: "감독들 프리셋에 있는 선수들 이름 중에 잘못 표기된 애들이 있어. 예를 들면 제주슨데 예수스, 하베르츤데 하버츠처럼. 사람들이 주로 그렇게 안 부르니까 다시 한 번 인터넷에서 검색해서 조사하고 이름 다 한 번씩 체크하면서 수정해줘. 그리고 전술판에 있는 선수 이름들 폰트도 바꿔줘 지금 우리 쓰는 폰트로" — 두 가지 요청. 예시로 든 "제주스→예수스"·"하베르츠→하버츠" 자체는 실제로 찾아보니 이미 올바르게(하버츠·예수스) 들어가 있었다 — 순수 예시(이런 유형의 실수를 찾으라는 뜻)로 받아들이고 전체 프리셋(감독 10개 + 실제 경기 2개, 총 172명)의 이름을 전부 웹 검색으로 대조했다.
- **조사 방법**: 각 프리셋 JSON의 `players[].name`을 전부 추출해 목록화한 뒤, 극히 유명한 이름(메시·호날두급)은 표준 표기가 명백해 제외하고, 표기가 갈릴 수 있는 이름(복합 성·외래어 표기 세칙이 실제 통용과 다른 경우) 위주로 WebSearch로 다음스포츠·나무위키·위키백과·공식 구단 홈페이지 등의 실제 표기 빈도를 확인했다. **원칙**: 국립국어원 표기 규정보다 **실제로 한국 축구 팬·매체가 가장 많이 쓰는 표기**를 우선한다(사용자가 명시한 "사람들이 주로 그렇게 안 부르니까" 기준) — 예를 들어 홀란(Haaland)은 국립국어원 권고 표기지만 "홀란드"가 훨씬 더 널리 쓰여 후자를 택함.

### 35. 전술 대결 패스 공 반복 재생

- **내용**: "전술 대결에서 패스길에 공이 계속 움직이면 좋겠어. 지금은 한번만 움직여." `AnnotationLayer.tsx`의 `PassChainBall`은 2026-09-10에 이미 한 번 논의된 이력이 있었다 — 당시 `repeat: Infinity`(계속 왕복)였던 걸 "한 번만 움직이고 도착점에 멈춤"으로 바꾼 게 그날의 결정이었다. 이번 요청은 사실상 그 결정을 정면으로 뒤집는 것처럼 보여서, 먼저 그 결정의 배경(편집기 도크스트링)을 확인했다.
- **문서화된 기존 결정과의 충돌 확인**: 2026-09-10 결정의 실제 이유는 두 가지 다 **편집기(EditorPage)에서만 나는 어긋남**이었다 — (1) 드리블(carry) 구간에서 선수는 한 번만 모프하고 멈추는데 공만 계속 왕복해 "선수는 도착했는데 공이 또 움직인다", (2) 병합된 시점을 스텝별로 재생할 때 각 스텝 사이 정지 구간(0.6~1.8초) 동안 선수는 이미 멈춰 있는데 공만 계속 왕복해 "선수는 가만있고 공만 움직인다". 전술 대결 뷰(`MatchupView`)의 선수 노드(`StaticPlayerNode`)는 두 분석의 **고정 스냅샷**이라 애초에 모프도 안 하고 시점 스텝 재생 기능도 없다 — 즉 2026-09-10에 문제였던 두 어긋남 자체가 이 컨텍스트에서는 구조적으로 일어날 수 없다. 그래서 "무조건 한 번만 재생"이 아니라 **컨텍스트별로 다르게** 가는 게 맞다고 판단해, 기존 결정을 지우는 대신 새 옵션으로 확장했다.
- **구현**: `AnnotationLayer`에 `loop?: boolean`(기본 `false`, 기존 동작 그대로) prop 추가 → `PassChainBall`까지 그대로 전달. `loop=true`일 때만 `transition`에 `repeat: Infinity, repeatDelay: 0.5`(PlayerNode의 run 반복 루프와 같은 대기 시간) 추가 — `repeatType`은 지정하지 않아 기본값 `'loop'`(역재생 없이 매번 처음부터 다시 재생)를 그대로 쓴다. 패스는 방향성이 있어서 왕복(reverse)으로 거꾸로 흐르면 어색하기 때문(PlayerNode의 run 반복 애니메이션과 같은 이유로 이미 그렇게 돼 있었다). `MatchupView.tsx`의 두 `<AnnotationLayer>` 호출(A팀·B팀)에만 `loop`를 켰다 — `EditorPage`·`SharePage`·`ShareCard`·`SharePngCard`·`AnimatedShareCard`의 기존 사용처는 전혀 안 건드려서 2026-09-10 결정이 여전히 유효한 곳에는 영향이 없다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(174, 회귀 없음)/`npm run build` 통과. 실제 테스트 계정을 새로 만들고 과르디올라·아르테타 프리셋을 각각 불러와 패스 화살표를 하나씩 직접 그려서 저장한 뒤, `/versus`에서 둘을 비교 화면에 띄우고 공(ellipse)의 좌표를 4.8초 동안 0.4초 간격으로 12번 샘플링 — 좌표가 시작점으로 반복해서 돌아오는 것을 확인(한 번만 재생됐다면 도착점 좌표에서 멈춰 있어야 함). 스크린샷으로도 두 팀의 점선 패스 화살표가 정상적으로 그려지는 것 확인. 테스트에 쓴 계정 9개(시행착오 중 누적된 것 포함)와 저장된 분석 8개는 `data/tacticore.db`에서 `PRAGMA foreign_keys = ON` 상태로 정리(단, `analyses`는 `user_id`에 `ON DELETE CASCADE`가 없어 분석을 먼저 지우고 사용자를 지우는 순서로 처리).
- **미확인**: 사용자가 브라우저에서 실제 저장된 분석 두 개로 전술 대결 화면을 열어 패스 공이 계속 흐르는지 확인해야 한다.

### 36. 전술 대결 뷰 5건 (구역 우세 골키퍼 제외·포지션 라벨+색상·노드 크기 축소)

- **내용**: "전술대결 페이지를 좀 손보자. 일단 구역별 우세한거를 전술판에 3:0 이런식으로 표현했잖아. 거기에 골키퍼 수는 빼자. 그리고 선수들 이름 옆에 포지션도 있으면 좋겠어. 예를 들면 FW일류첸코 이런식으로. 그리고 그 포지션에는 우리가 적용했던 포지션별 색깔도 적용하고, 전술판에 있는 선수들 글자 폰트도 우리가 쓰는거랑 동일하게 바꿔줘. 마지막으로 전술대결에서 전술판에 있는 선수들 노드 크기 좀 줄여줘." 5가지 요청.
- **1) 구역 우세 카운트에서 골키퍼 제외**: `computeOverload`(`lib/overload.ts`)는 에디터의 익명 상대 점 기반 오버로드와 공유하는 범용 함수라 수정하지 않았다 — 대신 `MatchupView.tsx`에 `excludeGoalkeepers(positions, players, formation)` 헬퍼를 추가해, `computeOverload`에 넘기는 `syntheticPhase.positions`/`opponentPositions`를 만들 때 양팀 GK를 `positionInfoAt(formation, index)?.line === 'GK'`로 걸러낸 뒤 넘긴다. 마커 자체(`StaticPlayerNode`)는 이 필터와 무관하게 GK를 계속 그린다 — 집계에서만 빼는 것이지 화면에서 지우는 게 아니다. `AdvantageBadge`(상단 요약 바)와 `MatchupOverloadLayer`(피치 위 3:0 숫자) 둘 다 같은 `zones` 변수를 공유해서 이 업스트림 수정 하나로 둘 다 함께 고쳐졌다.
- **2·3) 포지션 코드 + 포지션별 색상**: `StaticPlayerNode.tsx`의 이름 `<text>`에 `<tspan>` 두 개(포지션 코드 + 이름)를 넣어 "FW일류첸코"처럼 붙여 쓰고, 코드 tspan만 `POSITION_LINE_COLORS[info.line].fill`로 칠했다(GK 노랑/DF 파랑/MF 초록/FW 빨강 — `PrintPlayerNode`·`PlayerNode`·`SharePlayerNode`와 동일한 팔레트). 마커 원 색은 여전히 팀 색(`VERSUS_TEAM_COLORS`, 2026-09-07 결정)이라 이 결정을 뒤집지 않는다 — 파일 상단 docstring에 "마커 색 결정은 그대로, 라벨의 포지션 코드만 추가 정보"라고 명시해뒀다. `MatchupView.tsx`의 라벨 겹침 방지 박스 너비 계산(`labelBoxes`)도 이름 앞에 항상 2글자(GK/DF/MF/FW)가 붙는 만큼 `+2`로 보정했다.
