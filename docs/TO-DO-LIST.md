## 항목 상세

### 7. 분석 목록 고도화

- **내용**: 목록 화면에 썸네일 미리보기(base 국면 미니 렌더링), 제목·날짜 검색, 태그. 목록이 수십 개가 되면 필요.
- **기술 메모**: 썸네일은 저장 시점에 base 국면을 작은 PNG로 만들어 두는 방식(목록 조회 시 렌더링은 느림) — 백엔드에 파일 또는 BLOB 컬럼 필요.
- **구현**:
  - **백엔드**: `analyses.thumbnail`(Text — base64 PNG data URL 통째로 저장, 별도 파일/BLOB 관리 없이 DB 백업 하나에 다 들어가게), `analyses.tags`(SQLAlchemy `JSON` 타입 — SQLite에는 TEXT로 저장되지만 파이썬 `list[str]` ↔ DB 자동 (역)직렬화됨, 별도 다대다 태그 테이블은 이 규모엔 과해서 채택 안 함). 둘 다 기존 테이블이라 `main.py`의 `_ensure_column`으로 마이그레이션(`tags`는 `TEXT DEFAULT '[]'`로 기존 행도 빈 배열이 되게). `schemas.py`의 `AnalysisIn`/`AnalysisSummary`에 두 필드 추가.
  - **썸네일 생성**: 새 `components/export/ThumbnailCard.tsx` — `SharePngCard`/`ShareCard`와 같은 "화면 밖(-9999px) 고정 크기 노드 캡처" 패턴이지만, store 의존 없는 읽기 전용 노드(`SharePlayerNode`/`PrintOpponentNode`)로 base 국면 피치만 작게(160×247, 68:105 비율) 그린다. `lib/exportImage.ts`에 `captureThumbnail`(기존 `exportCard`와 달리 다운로드 안 하고 data URL만 반환) 추가. `SaveButton.tsx`가 저장 버튼을 누를 때마다 이 카드를 캡처해 페이로드에 실어 보낸다 — 캡처 실패는 저장을 막지 않고 기존 썸네일을 그대로 둔다. `DuplicateButton`은 별도 캡처 없이 원본 `analysis.thumbnail`을 그대로 이어받는다(페이로드 스프레드에 이미 포함돼 있어서 코드 변경 불필요).
  - **태그 입력**: 새 `components/editor/TagInput.tsx` — Enter(또는 쉼표)로 하나씩 추가, 칩의 ×로 삭제. 매 글자마다 store에 커밋하지 않고 확정 시점(Enter/blur)에만 커밋 — 다른 목록형 편집(annotations 등)과 같은 패턴. "경기 정보" 섹션에 `MatchInfoForm` 바로 아래 배치.
  - **검색·태그 필터**: `AnalysesPage.tsx`에서 처리 — 목록이 수십 개 규모라 서버 왕복 없이 이미 받아온 데이터를 프론트에서 걸러낸다(매치명·팀·날짜 텍스트 검색 + 태그 칩 클릭으로 필터, 클릭한 태그 다시 클릭하면 해제). 새 API 불필요.
  - **목록 표시**: `AnalysisList.tsx`에 썸네일 열(작은 `<img>`, 없으면 점선 테두리 자리표시자)과 태그 열(칩) 추가.
  - 구버전 JSON(감독 프리셋, 기존 내보내기 파일)엔 `tags`가 없을 수 있어 `lib/schema.ts`의 zod 스키마에 `.optional().default([])`로 하위호환.
- **일별/주별 그룹핑(2026-09-09 후속 요청)**: "저장목록을 하루마다 혹은 일주일마다 끊으면 좋겠다" — 새 순수 함수 `lib/dateGrouping.ts`의 `groupByDate`(경기 일자 `matchDate` 기준. 언제 저장했는지가 아니라 그 경기가 언제였는지가 라이브러리를 훑어볼 때 더 자연스럽다고 판단). 주별은 월요일 시작 주 단위, 라벨은 "MM/DD ~ MM/DD". `AnalysesPage.tsx`에 전체/일별/주별 3단 토글 칩 추가(기존 태그 필터 칩과 같은 스타일) — 기본값은 "전체"(기존 동작 그대로, 그룹핑은 켜야 나옴). 그룹별로 기존 `AnalysisList`를 그대로 재사용해 섹션 제목만 얹는다(`AnalysisList` 자체는 안 건드림). vitest로 `groupByDate` 유닛 테스트(7개: 같은 날/주 묶임, 내림차순 정렬, 그룹 내 순서 보존, 다음 주 분리, 라벨 형식, 빈 입력).
- **타임라인 관련 버그 2건도 이번에 같이 수정** (사용자가 목록 그룹핑을 요청하면서 함께 리포트):
  1. **"Failed to fetch" 저장 실패**: 원인은 이 세션에서 Claude가 테스트 데이터를 정리하며 파이썬 `sqlite3`로 직접 `DELETE FROM analyses`를 실행한 것 — 이 프로젝트의 FK 연쇄삭제(CASCADE)는 `backend/database.py`가 SQLAlchemy 엔진 연결마다 켜는 `PRAGMA foreign_keys=ON`에만 의존하는데, raw sqlite3 연결은 이걸 안 타서 조용히 무시됨. 그 결과 `players`/`phases`/`positions`/`annotations`에 고아 행이 남았고, `analyses.id`가 `AUTOINCREMENT` 없는 평범한 정수 PK라 삭제된 id가 재사용되면서 새 저장이 고아 행과 `UNIQUE(analysis_id, client_id)` 제약에 충돌해 500 에러가 났다. 브라우저에는 이게 CORS 에러("Failed to fetch")로 잘못 표시됨(Starlette가 처리 안 된 예외 응답에 CORS 헤더를 못 붙이는 경우가 있어서). 고아 행(선수 27개, 국면 6개 및 파생 좌표·화살표) 전부 정리해 해결 — 코드 변경은 없음, 순수 데이터 정리. 앞으로 테스트 데이터 정리는 항상 앱 API 또는 ORM 세션으로만 하도록 메모리에 기록.
  2. **"+ 시점"으로 만든 기본 이름이 "체인징 포인트 N"**: 버튼·안내 문구는 전부 "시점"인데 기본 이름만 내부 개발 용어가 새어나가 있었음 — "시점 N"으로 통일(`Timeline.tsx`).
  3. **"0'" 눈금과 "시간 미정" 칩 줄이 겹침**: 원인은 CSS 우선순위 — 부모의 `space-y-1`이 만드는 자식 간격 규칙이 일반 `mb-*` 유틸리티보다 우선순위가 높아 축 div가 부모 직계 자식인 한 어떤 margin-bottom도 0으로 덮어써지고 있었다(디버깅 중 발견, 처음엔 vite 캐시 문제로 오인해 여러 번 재기동하며 값을 키웠으나 효과 없었던 게 실마리). 한 겹 더 감싸 직계 자식 관계를 끊어서 해결.
- **검증**: `tsc --noEmit`/`eslint`/`vitest run`(신규 `dateGrouping.test.ts` 7개 포함 149 tests 통과)/`npm run build` 통과(빌드 후 `dist/` 삭제). Playwright로 실제 브라우저 E2E: 회원가입 → 서로 다른 날짜(2026-09-01, 2026-09-08 — 다른 날·다른 주)의 감독 프리셋 2개 저장 → 목록에서 기본(전체) 뷰는 헤딩 없이 평평하게 표시 확인 → 일별 토글 시 날짜별 헤딩 2개(각각 정확한 날짜) 확인 → 주별 토글 시 주별 헤딩 2개(최근 주가 위) 확인 → 전체로 되돌리면 헤딩 사라짐 확인. 타임라인 버그 2건도 각각 실제 브라우저로 재현 후 수정 확인(시점 추가 후 저장 성공, 기본 이름 "시점 1" 확인, 겹침 해소를 실제 좌표 측정으로 확인). 5개 체크 전부 통과. 정리 과정에서 사용자 소유 분석 목록에 "안첼로티" 프리셋이 중복 없이(복제 표시 없이) 한 건 더 있는 걸 발견했으나, 사용자가 버그 재현 확인 과정에서 직접 저장했을 가능성이 있어 — Claude가 만든 게 확실하지 않은 데이터라 — 삭제하지 않고 그대로 둠(필요하면 목록에서 직접 삭제 가능).
- **검증**: `tsc --noEmit`/`eslint`(기존 경고 2건 외 신규 없음)/`vitest run`(142 tests 통과)/`npm run build` 통과(빌드 후 `dist/` 삭제). 백엔드 마이그레이션이 실제 로컬 DB에 `thumbnail`/`tags` 컬럼을 만들고 기존 26건이 안 깨지는지 확인. Playwright로 실제 브라우저 E2E: 회원가입 → 감독 프리셋 로드(빈 포메이션은 홈/원정팀·선수 이름이 비어 있어 저장 시 422가 나는 걸 처음에 발견 — 프리셋으로 바꿔서 재검증) → 태그 2개 입력(칩 2개 렌더링 확인) → 저장(JS 에러 없음 확인) → 저장 목록에서 실제 PNG data URL 썸네일 렌더링·태그 칩 표시 확인 → 검색어로 좁혀지는 것과 없는 검색어로 "조건에 맞는 분석이 없습니다" 문구 확인 → 태그 칩 클릭으로 필터링 확인. 7개 체크 전부 통과, 스크린샷으로 실제 미니 피치 썸네일까지 육안 확인. 테스트 중 두 차례(첫 시도의 빈 포메이션 422, 스크립트의 타임아웃) 발생한 부수적인 테스트 계정 잔여물을 포함해 전부 정리, 실제 사용자 계정(26건)은 그대로 둠.

### 9. 실제 경기 명장면 프리셋 (StatsBomb OpenData)

- **내용**: 원래 원했던 "실제 경기 분석"의 부분 실현. StatsBomb OpenData(무료, GitHub 공개)의 이벤트 데이터에는 슈팅 순간 양 팀 전원의 실제 좌표(freeze frame)가 담겨 있어, 이를 국면 프리셋으로 변환하면 "2022 월드컵 결승 결승골 장면" 같은 실제 배치를 불러올 수 있음.
- **제약 (중요)**: 슈팅 장면 위주(전 경기 트래킹 아님), 좌표계 변환(StatsBomb는 0~120 × 0~80) 필요, 원본 JSON이 커서 사전 가공 스크립트 필요. 작업량 중~대.
- **연혁**: "실제 경기를 DB에서 검색해 자동 분석"은 2026-09-01 무료 API가 국면별 선수 좌표를 제공하지 않아 기각 → 감독 프리셋으로 대체. 이 항목은 그 대안의 확장.
