## 항목 상세

### 61. 기본 SEO(robots.txt·sitemap.xml·시맨틱 태그) 추가

- **내용**: "구글에 tacticraft 검색했는데 아예 안 떠. 축구 전술 사이트로 검색했을때도 뜨게 하고 싶은데 방법이 없을까?" — 배포(TO-DO 59) 당일이라 구글이 아직 한 번도 크롤링을 못 한 게 근본 원인(버그 아님)이었다. 사용자에게 두 목표를 분리해서 설명했다: (1) "tacticraft" 브랜드 검색은 경쟁자가 없어 색인만 되면 금방 뜬다, (2) "축구 전술 사이트" 같은 일반 키워드는 콘텐츠·백링크·시간이 쌓여야 하는 장기전이라 지금 당장 켤 수 있는 스위치가 아니다 — 과장하지 않고 지금 할 수 있는 기술적 조치만 진행했다.
- **구현**:
  - **`robots.txt`/`sitemap.xml` 신설**: 둘 다 원래 존재하지 않아서 `/robots.txt` 요청이 FastAPI의 SPA 폴백(`main.py`의 `serve_frontend`)에 걸려 `index.html`을 돌려주고 있었다(실제 robots.txt가 아님 — `curl`로 확인). `frontend/public/robots.txt`(전체 허용 + sitemap 위치)와 `frontend/public/sitemap.xml`(정적 최상위 라우트 3개 — `/`·`/new`·`/community`)을 새로 추가했다. `/share/:id`·`/analyses/:id` 같은 동적 라우트는 사용자 생성 콘텐츠라 정적 사이트맵에 미리 나열할 수 없어 뺐다(필요해지면 동적 사이트맵 생성기가 별도 작업).
  - **홈 화면 태그라인을 `<h1>`으로**: `EditorPage.tsx`의 빈 화면 태그라인이 그냥 `<p>`였다 — 이 문구가 사실상 사이트를 설명하는 유일한 텍스트인데 검색엔진이 페이지 주제를 판단할 때 가장 크게 보는 `<h1>`이 아예 없었다. 클래스는 그대로 둬서 화면엔 변화 없이 태그만 `<h1>`로 바꿨다.
  - **`<title>`에 키워드 추가**: `TactiCraft` 단독이던 페이지 제목을 `TactiCraft — 축구 전술 분석 & 공유`로 바꿨다 — `<title>`은 구글 검색 순위에서 가장 비중이 큰 신호 중 하나인데 브랜드명만 있으면 일반 키워드 검색에 전혀 안 걸린다. "TactiCraft"를 맨 앞에 둬 브라우저 탭·검색 결과 제목 둘 다 브랜드가 먼저 보이게 하면서 뒤에 실제 검색 키워드를 붙였다.
  - **`<html lang="en">` → `lang="ko"` 수정**: 위 작업 중 발견한 별개의 실제 결함 — `CLAUDE.md`에 "문서와 UI는 한국어 단일 언어"라고 명시돼 있는데 `lang` 속성은 계속 `en`이었다. 검색엔진이 언어를 오판하면 한국 사용자에게 이 페이지를 덜 보여줄 수 있어 SEO에도 직접 영향이 있다.
  - **미착수(사용자 계정 필요)**: Google Search Console 등록(소유권 확인용 메타 태그는 코드에 추가할 수 있지만, 계정 생성·확인 자체는 사용자의 구글 계정으로 직접 해야 함) + 사이트맵 제출 + 홈페이지 "색인 생성 요청"(자연 크롤링보다 훨씬 빠르게 색인됨) — 사용자에게 다음 단계로 안내했고, 진행 여부는 사용자 선택.
- **검증**: 프론트 `tsc -b`(0 errors) / `npm run lint`(0 errors) / `npx vitest run`(208 전부 통과, `<h1>` 변경으로 깨진 테스트 없음) / `npm run build` 성공(빌드 산출물에 `robots.txt`·`sitemap.xml` 포함 확인). Fly.io 재배포 후 `curl`로 `https://tacticraft.fly.dev/robots.txt`가 실제 robots.txt 내용을 반환(더 이상 `index.html` 폴백 아님), `sitemap.xml` 200, `<html lang="ko">`·새 `<title>` 전부 실서비스에서 확인했다.
- **미확인**: 이 조치들이 실제로 구글 색인·검색 노출로 이어지는지는 크롤링 주기(며칠~몇 주) 때문에 이 세션에서 확인 불가능하다 — 사용자가 나중에 "tacticraft" 검색으로 직접 확인해야 한다. Search Console 등록도 사용자가 아직 진행 전이라 사이트맵 제출·수동 색인 요청은 안 된 상태다.
- **후속 작업(같은 날, "검색엔진에 걸리게 메타데이터 설정해줘")**: 계정 없이 바로 넣을 수 있는 메타데이터를 추가했다 — `<meta name="keywords">`(구글은 2009년부터 순위 신호로 안 쓰지만 harmless, 일부 국내 검색엔진은 여전히 참고 가능), `<meta name="robots" content="index, follow">`(명시적 선언), `<link rel="canonical">`(SPA라 `/versus?a=33` 같은 쿼리스트링 변형이 별도 페이지로 오인되지 않게 정식 URL을 못 박음), `Schema.org WebSite` 구조화 데이터(JSON-LD) — 검색엔진이 사이트명·URL·설명을 명확한 구조로 읽게 한다(전역 검색 기능이 없어 SearchAction은 뺐다). 한국어 사이트라 네이버 서치어드바이저 등록도 제안했으나(구글보다 한국 사용자 도달에 더 효과적일 수 있음) 이것도 사용자 본인 계정이 필요해 아직 미착수 — Google Search Console과 마찬가지로 사용자가 인증 코드를 주면 진행하기로 안내했다.
- **Google Search Console 등록 완료(같은 날, "구글이랑 네이버 둘 다 등록할게")**: 사용자가 이미 브라우저에 구글로 로그인돼 있어(claude-in-chrome이 같은 브라우저 프로필을 공유) 세션이 직접 진행했다 — 속성 추가(URL 접두어 방식, 도메인 방식은 DNS 인증이 필요해 fly.dev 하위 도메인 소유권을 증명할 수 없어 제외) → HTML 태그 인증값을 `index.html`에 `<meta name="google-site-verification">`로 추가·재배포 → "확인" 클릭해 소유권 인증 성공 → 사이트맵(`sitemap.xml`) 제출(처음엔 "가져올 수 없음"으로 떴다가 몇 분 뒤 재확인하니 "성공"으로 바뀜 — 비동기 처리라 그런 것이었다) → 홈페이지 URL 검사 후 "색인 생성 요청" 클릭해 접수 완료. **네이버 서치어드바이저는 claude-in-chrome의 안전 정책상 해당 도메인 접속이 막혀 있어 세션이 대신 진행할 수 없다** — 사용자가 직접 로그인해 인증 코드를 주면 이어서 처리하기로 했다(아직 미착수).
- **버그로 착각했던 해프닝**: `curl -I`(HEAD 요청)로 `robots.txt`/`sitemap.xml`/홈페이지의 `Content-Type`을 확인했더니 전부 `application/json`으로 잘못 나와서 실제 배포 버그로 의심하고 원인을 깊이 팠다 — 로컬 백엔드 직접 호출, Starlette `FileResponse` 소스 확인, 프로세스 재기동까지 하며 조사했으나, **실제로는 HEAD 요청에서만 나타나는 현상이고 진짜 GET 요청(`curl -sv`로 확인)은 로컬·배포 환경 둘 다 정확한 `Content-Type`(`text/xml`, `text/plain`, `text/html`)을 반환**했다. 구글 크롤러·브라우저·카카오톡 등 실제 트래픽은 전부 GET을 쓰므로 실사용에는 영향이 없는, `curl -I` 사용법 때문에 생긴 잘못된 신호였다 — 코드 수정 없이 조사만으로 종결.
- **네이버 서치어드바이저 등록 완료(2026-09-18)**: claude-in-chrome이 `searchadvisor.naver.com` 접속 자체를 안전 정책상 막아서 이번엔 세션이 대신 못 하고 사용자가 전 과정을 직접 진행했다 — 사용자가 네이버에서 발급받은 HTML 태그 인증값(`<meta name="naver-site-verification" content="...">`)을 채팅으로 전달 → 세션이 `index.html`에 추가·재배포·`curl -sv`(GET)로 실제 반영 확인 → 사용자가 네이버 화면에서 "확인" 클릭해 소유 확인 성공(첫 시도는 "메타태그를 찾을 수 없습니다" 오류였는데, 그건 세션이 아직 태그를 배포하기 전에 사용자가 먼저 확인을 눌러서 난 정상적인 실패였다 — 순서 문제였지 버그 아님) → 사용자가 사이트맵(`https://tacticraft.fly.dev/sitemap.xml`) 제출 + 웹 페이지 수집 요청까지 전부 완료. 이걸로 구글·네이버 둘 다 소유 확인·사이트맵 제출·색인(수집) 요청이 끝났다 — 남은 건 각 검색엔진이 실제로 크롤링해 검색 결과에 반영하는 시간(수 시간~수일, 새 도메인이라 더 걸릴 수도 있음)뿐이고, 이건 세션이 통제할 수 없는 영역이라 이 항목은 여기서 마무리한다.

### 62. 공개 범위 3단계(비공개/링크 공개/커뮤니티 공개) 재설계

- **배경**: 사용자가 정리한 `docs/개선_로드맵.md`(2026-09-18 편입) §5.2가 지적한 P0 실제 취약점 — `is_public=false`(비공개)인 분석도 `GET /api/analyses/{id}`가 로그인 여부와 무관하게 항상 응답해서, `id`가 1,2,3… 순차 정수라 스캔하면 비공개 분석도 그대로 읽혔다(공유 링크와 편집기 로드가 같은 id 기반 엔드포인트를 공유하던 구조). 로드맵 저장 직후 "우선순위 논의부터 하고 구현하자"는 요청으로 P0 6개 항목의 위험도를 다시 정리해 제시했고, 사용자가 "5.2 공개 범위 재설계"를 먼저 선택 → 2단계(비공개/커뮤니티)로 단순화할지 로드맵 원안대로 3단계(비공개/링크/커뮤니티, 토큰 기반)로 갈지 다시 물어 **3단계로 확정**했다.
- **구현**:
  - **DB**: `analyses.is_public`(불리언) 대신 `visibility`(`private`\|`link`\|`community`, 기본 `private`)와 `share_token`(추측 불가능한 랜덤 문자열, `secrets.token_urlsafe(16)`) 컬럼을 추가했다(`_ensure_column`, `main.py`). `is_public` 컬럼 자체는 SQLite `DROP COLUMN`의 구버전 호환 위험을 피하려고 죽은 컬럼으로 남겨 두고 앱 코드에서는 더 이상 읽거나 쓰지 않는다. 기존 데이터는 1회성 백필로 이관했다 — `is_public=1`이던(이미 완전 공개였던) 분석은 `visibility='community'`로 승격해 기존 공유 링크·좋아요·댓글이 안 깨지게 했고, `is_public=0`이던 분석은 기본값 `private` 그대로 뒀다("링크 공개"는 이 컬럼이 생기기 전엔 존재하지 않던 중간 단계라 소급 적용할 근거가 없었음). 실제 로컬 DB에서 백필을 실행해 `is_public=1`이던 분석 1건(id=33)이 정확히 `community`로 이관되고, 나머지 전부 `private` + 고유 토큰을 받는 것을 확인했다.
  - **접근 제어**: `GET /api/analyses/{id}`는 이제 소유자 또는 `visibility='community'`만 볼 수 있다(그 외엔 403이 아니라 404 — 존재 여부 자체를 노출하지 않음). `visibility='link'`인 분석은 id로는 절대 안 열리고, 새 엔드포인트 `GET /api/share/{token}`으로만 열린다(id는 순차 정수라 그 자체로 비밀이 될 수 없다는 게 애초 취약점의 핵심이라, "링크 공개"가 의미를 가지려면 id와 무관한 추측 불가능한 값이 필요했다). 댓글 읽기/쓰기(`comments.py`)와 좋아요 토글(`community.py`)에도 같은 `crud.is_visible_to(row, user_id)` 검사를 추가했다 — 이전엔 `analysis_id`만 맞으면 댓글·좋아요 API가 비공개 분석에도 그대로 뚫려 있었다(분석 본문은 막혀도 댓글·좋아요는 새는 사각지대였음). **로드맵 §5.2의 표는 "링크 공개는 댓글·좋아요가 소유자 설정에 따름"이라고 적었지만, 이번 구현은 링크 공개면 댓글·좋아요를 항상 허용한다** — 소유자가 댓글/좋아요만 따로 껐다 켰다 하는 토글은 요청받지 않았고 로드맵에도 그 UI 설계는 없어서, 이 항목만으로 임의로 만들지 않았다(요청 없이 기능을 얹지 않는다는 원칙). 필요해지면 별도 TO-DO로 다룬다.
  - **공유 링크 모양**: "커뮤니티 공개"는 기존과 똑같이 `/share/:id`를 그대로 쓴다(이미 완전 공개였던 상태라 숨길 이유가 없고, 기존에 공유된 링크가 안 깨져야 했음). "링크 공개"는 새 라우트 `/s/:token`(백엔드 `/api/share/{token}` 호출). 프론트 `SharePage.tsx`를 `ShareView` 공용 렌더링 + `SharePage`(id)/`SharedLinkPage`(token) 두 얇은 래퍼로 리팩터링했다 — 렌더링 로직은 100% 동일, fetch 방식만 다르다.
  - **에디터 UI**: 기존 이진 토글 `CommunityShareToggle`("커뮤니티에 공유" on/off)을 삭제하고 3지 선택 `VisibilitySelect`(비공개/링크 공개/커뮤니티 공개, `PATCH /api/analyses/:id/visibility`)로 교체했다. `ShareLinkButton`도 공개 범위별로 분기한다 — 비공개면 버튼 비활성화(안내 문구), 링크 공개면 `/s/:token`, 커뮤니티 공개면 `/share/:id`.
  - **실사용 중 발견해 같이 고친 사이드 버그**: 분석을 막 저장(POST/PUT)한 직후엔 라우터가 `is_owner`/`share_token`을 응답에 채워 넣지 않고 있었다(원래 `crud.to_analysis_dict(row)`를 그대로 반환) — 생성 직후 곧바로 "링크 공개"로 바꾸면 프론트 스토어에 `shareToken`이 없어 `/s/undefined` 링크가 만들어지는 문제로 이어질 뻔했다. 생성자는 항상 소유자이므로 `create_analysis`/`update_analysis` 응답에 `is_owner: True`, `share_token: row.share_token`을 명시적으로 채우도록 고쳤고, 프론트 `applySavedMeta`/`SaveButton`도 저장 응답의 `visibility`/`shareToken`을 스토어에 반영하도록 확장했다.
- **검증**:
  - 프론트: `tsc -b`(0 errors) / `npm run lint`(0 errors, 기존 경고 3개는 이 작업과 무관) / `npx vitest run`(208 전부 통과).
  - 백엔드: 클린 uvicorn 인스턴스를 띄우고(`backend-reload-stale-process` 메모리대로 중복 프로세스부터 정리) 실제 회원 2명(소유자/타인)으로 `curl`을 통해 접근 제어 행렬 전체를 실제 HTTP 요청으로 검증했다 — ① 비공개: 비로그인·타인 id 접근 404, 소유자 접근 200, 토큰이 있어도 비공개면 404. ② 링크 공개: id 접근(비로그인·타인 모두) 404, 토큰 접근(비로그인·타인 모두) 200. ③ 커뮤니티 공개: id 접근 200(비로그인 포함), 커뮤니티 목록에 노출. ④ 댓글·좋아요: 비공개 분석에 타인이 접근 시 404, 소유자는 200. ⑤ 기존에 이미 공개돼 있던 분석(id=33, 마이그레이션으로 `community` 승격)이 여전히 id로 정상 조회됨(하위호환 확인).
  - **미확인**: 에디터의 `VisibilitySelect`/`ShareLinkButton` 실제 클릭 동작은 브라우저로 시각 검증하지 못했다 — 이 세션의 셸(Bash/PowerShell 도구)이 띄운 Vite dev 서버가 실제 사용자 브라우저가 보는 Windows 호스트 네트워크와 분리된 샌드박스에 있어서, claude-in-chrome으로 `localhost:5173`에 접속했더니 이 세션이 띄운 TactiCraft가 아니라 호스트에 이미 떠 있던 무관한 다른 프로젝트("My Asset Manager", 참고 프로젝트로 추정)가 응답했다 — 셸 도구 network와 실제 브라우저 network가 이 환경에서 일치하지 않는다는 뜻이라, 이 세션에서는 더 시도해도 해결 불가로 판단해 중단했다. 백엔드 로직(접근 제어의 핵심)은 위처럼 실제 HTTP 요청으로 충분히 검증했지만, 3지 선택 드롭다운의 실제 클릭감·공유 링크 복사 버튼 문구 전환은 사용자가 본인 브라우저에서 직접 확인해야 한다.

### 63. 초안 자동복구 + 이탈 방지

- **배경**: 개선 로드맵 §5.1(P0) — "새로고침 한 번에 작업이 날아간다"는 체감 임팩트가 큰 문제. 62번(공개 범위) 완료 후 "나중에 확인할게 다음거 진행해줘"로 이어서 착수했다. 로드맵이 제시한 완료 기준 3개(새로고침 후 복구 가능 / 어떤 메뉴를 눌러도 미저장 변경이 조용히 안 사라짐 / 서버가 죽어도 로컬 복구 가능) 중 세 번째는 이미 기존 구조(FR-08 폴백 — 백엔드 꺼져도 편집 가능)로 충족돼 있었고, 이번엔 첫째·둘째를 구현했다.
- **구현**:
  - **로컬 자동 백업**(`frontend/src/lib/draftStorage.ts`, `hooks/useDraftAutosave.ts`): `isDirty`인 동안 편집이 4초간 멈추면 현재 `analysis`를 `localStorage`(고정 슬롯 하나 — 이 앱은 한 번에 하나만 편집하므로 여러 초안 관리는 과설계)에 저장한다. `isDirty`가 false가 되는 모든 경우(서버 저장 성공, 다른 분석 로드, 복구 배너에서 "버리기")에 초안을 즉시 지우는 단일 규칙으로 "저장 성공 후 정리"·"명시적으로 버린 뒤 정리"를 한꺼번에 처리한다 — 각 호출부에 따로 정리 로직을 심을 필요가 없다. `localStorage` 접근은 전부 try/catch로 감싸서 프라이빗 브라우징 등에서 던져도 편집 자체는 안 막는다(vitest가 jsdom 없이 Node 환경에서만 돌아 `localStorage`가 없다는 것도 이 세션에서 직접 확인했다 — 그래서 draftStorage.ts 자체의 유닛 테스트는 추가하지 않았고, `analysisStore.test.ts`에 새로 추가한 `restoreDraft` 테스트로 스토어 쪽 로직만 커버했다).
  - **복구 배너**(`components/editor/DraftRecoveryBanner.tsx`): `EditorPage` 마운트 시 `localStorage`에 남은 초안이 있으면 "저장하지 않은 초안이 있습니다 (n분 전 자동 저장됨) · [복구하기] [버리기]"를 띄운다. 스토어가 아니라 `localStorage`를 직접 읽으므로, `/analyses/:id` 새로고침으로 서버의 "깨끗한" 버전이 먼저 로드돼 있어도 그 위에 초안을 복구할 수 있다. 새 스토어 액션 `restoreDraft`(기존 `loadAnalysis`와 동일하지만 `isDirty: true`로 남김 — "서버에 없는 상태"라는 걸 표시해야 저장 버튼·자동 백업이 정상 동작)를 추가했다.
  - **새로고침·탭 종료 경고**(`hooks/useUnsavedChangesWarning.ts`, `App.tsx`에 전역 등록): `isDirty`일 때 `beforeunload`에 네이티브 브라우저 확인창을 띄운다. 전엔 로고 클릭에만 `window.confirm` 경고가 있었다.
  - **메뉴 이동 시 이탈 방지 확장**(`components/common/GuardedLink.tsx`): "메뉴를 눌러도 조용히 안 사라짐"을 실제로 위협하는 지점만 골라 가드를 달았다 — 저장 목록(`AnalysisList.tsx`)에서 다른 분석을 클릭해 `/analyses/:id`로 이동하는 링크(에디터 스토어를 다른 분석으로 덮어씀), `/new`에서 포메이션·프리셋을 선택하는 순간(`NewAnalysisPage.tsx` — `/new` 페이지 자체를 둘러보는 건 스토어를 안 건드려서 안전하므로 링크가 아니라 "선택" 동작에 확인을 걸었다). `/community`·`/versus`·`/share`처럼 에디터 스토어를 안 건드리는 화면은 가드가 필요 없어 그대로 뒀다. `RecentAnalyses.tsx`(빈 화면 전용 위젯)는 렌더 조건상 `isDirty`가 항상 false라 가드가 아예 발동할 수 없어 손대지 않았다(존재할 수 없는 시나리오에 방어 코드를 추가하지 않는다는 원칙).
  - **저장 상태 가시성**(`SaveButton.tsx`): "저장 *"(dirty)만으론 로컬 백업 여부가 안 보여서, dirty일 때 "변경사항은 이 브라우저에 자동 백업됩니다" 텍스트를 상시 노출한다(disabled-button-visible-hint 메모와 같은 이유로 hover 툴팁이 아니라 항상 보이는 텍스트).
- **advisor 리뷰로 구현 직후 발견해 고친 버그 3개**(코드는 작성했지만 아직 커밋 전이라 별도 항목 없이 여기 기록):
  1. **초안 자동 소멸 버그(치명적)**: `useDraftAutosave`가 "isDirty가 false면 지운다"만 있어서, 페이지를 막 열었을 때(아직 아무것도 안 건드려 isDirty=false인 순간)의 첫 이펙트가 방금 복구했어야 할 초안을 곧바로 지워버렸다 — 특히 `/analyses/:id`는 로딩 중(analysis=null)에서 데이터 도착(loadAnalysis, isDirty=false)으로 바뀌며 `DraftRecoveryBanner`가 다른 JSX 분기로 리마운트되는데, 그 사이 초안이 이미 지워져 배너 자체가 안 뜨는 경로가 있었다. `hasBeenDirtyRef`로 "이 마운트 동안 한 번이라도 실제로 dirty였을 때만" 지우도록 게이트를 추가했다.
  2. **`share_token` 유니크 인덱스 누락**: `models.py`의 `share_token = Column(..., unique=True, index=True)`는 `_ensure_column`(ALTER TABLE)으로 컬럼만 추가할 뿐 인덱스는 반영하지 않는다(`users.username`이 겪었던 것과 같은 함정, `_backfill_usernames`가 이미 이 패턴대로 별도 `CREATE UNIQUE INDEX`를 하고 있었는데 62번 작업 때 놓쳤다). `_backfill_visibility_and_tokens` 뒤에 `CREATE UNIQUE INDEX IF NOT EXISTS ix_analyses_share_token`을 추가하고, 로컬 DB에 실제 적용해 인덱스 생성과 토큰 중복 없음을 확인했다.
  3. **초안에 썸네일(큰 base64 PNG)까지 통째로 저장**: `SaveButton`이 저장 때마다 다시 캡처해 채우는 파생값이라 초안엔 불필요한데, 계속 들고 있으면 `localStorage` 용량 제한(도메인당 보통 5~10MB)에 걸려 "변경사항은 자동 백업됩니다" 안내와 달리 조용히 저장이 실패할 위험이 있었다. `saveDraft`에서 `thumbnail`을 제외하도록 고쳤다.
- **검증**: 프론트 `tsc -b`(0 errors) / `npm run lint`(0 errors, 기존 경고 3개는 무관) / `npx vitest run`(209개, 새로 추가한 `restoreDraft` 테스트 포함 전부 통과). **브라우저 시각 검증은 62번과 같은 이유(세션 환경의 셸 dev 서버 ≠ 실제 브라우저 네트워크, [[shell-sandbox-vs-real-browser-network]])로 못 했다** — 복구 배너 노출·자동 백업 타이밍·새로고침 경고창은 사용자가 직접 확인해야 한다.

### 64. DB 백업·복구 절차 + 헬스체크 DB 확인

- **배경**: 개선 로드맵 §5.4(P0). 63번 완료 후 advisor에게 다음 단계를 물었더니, §5.4가 성격이 다른 세 가지(Alembic 전환·자동 백업·헬스체크)를 한데 묶고 있고 순서 문제가 있다는 지적을 받았다 — **62번(공개 범위)의 `_ensure_column`+백필이 아직 프로덕션(Fly.io)에 배포·반영되지 않은 상태**라, 지금 Alembic으로 베이스라인을 잡으면 로컬과 다른 프로덕션 스키마를 기준으로 잡는 사고가 날 수 있다는 것. 그래서 이번엔 **백업/복구 + 헬스체크만** 진행하고, Alembic 전환과 `fly.toml`/`.github/workflows/` 변경은 미룬다(인프라·CI 변경은 명시적 허락이 필요한 영역이기도 함).
- **구현**:
  - **로컬 백업 스크립트**(`scripts/backup_db.py` + `scripts/backup-db.ps1`): 파일을 그냥 복사하는 대신 `sqlite3.Connection.backup()`(SQLite 자체의 온라인 백업 API)을 쓴다 — 서버가 켜진 채 쓰기 중이어도 일관된 스냅샷이 나온다(6단계 운영 매뉴얼의 예전 절이 "서버 종료 후에만 복사"를 권했던 것과 달리, 이제 서버를 안 내려도 된다). `data/backups/`에 타임스탬프 파일로 쌓이고 기본 최근 14개만 유지(오래된 것 자동 삭제) — `data/`가 통째로 gitignore 대상이라 백업 파일도 커밋되지 않는다.
  - **헬스체크가 DB까지 확인**(`backend/main.py`의 `/api/health`): 전엔 uvicorn 프로세스만 살아있으면 무조건 `{"status":"ok"}`였다 — SQLite 파일이 없어졌거나 잠겨 있어도 구분 못 했다. 이제 매 요청마다 가벼운 `SELECT 1`을 실행하고 실패하면 503을 준다. 프론트 `useServerHealth`는 `isServerUp`을 `query.isSuccess`(2xx 여부)로만 판정하므로 503도 자동으로 "서버 다운"과 동일하게 저장/목록 UI를 비활성화한다 — **프론트 코드는 한 줄도 안 바꿔도 됐다.**
  - **복구 절차 문서화**(`docs/6단계_운영_매뉴얼.md`): §3.2(백업)를 새 스크립트 기준으로 갱신하고, §3.6(로컬 복구 절차)·§3.7(Fly.io 배포본 백업)을 신설했다. Fly.io 프로덕션 DB를 실제로 내려받는 명령(`flyctl ssh sftp get`)은 절차만 문서화했고 **세션이 직접 실행하지는 않았다** — 운영 데이터 접근이라 사용자 승인 없이 자동 실행하지 않는다는 원칙(advisor 권고와도 일치).
  - **문서 정정(작업 중 발견)**: §3.5(스키마 변경 시)가 이미 2026-09-11에 제거된 "JSON 내보내기/가져오기" 기능에 의존하는 절차를 여전히 안내하고 있었다 — 실행 불가능한 지시였다. 실제로 지금 스키마 변경에 쓰이는 방식(`_ensure_column`/`_backfill_*` 패턴, DB를 지우지 않고 자동 반영)으로 다시 썼고, §4 전체(JSON 입출력 가이드)에도 "기능 제거됨" 경고를 얹었다. 문서 최상단 안내("공개 배포 없이 PC에서 로컬 실행")도 2026-09-01 작성 당시 기준이라는 걸 명시하고 실제 배포 상태(Fly.io, 2026-09-17)를 링크했다 — 이 문서 전체를 다 훑진 않았으니 다른 절에도 비슷한 시차가 남아있을 수 있다.
- **검증**:
  - 백엔드: `python -c "import main"`으로 마이그레이션·인덱스·헬스체크 로직이 실제로 실행됨을 확인. 클린 uvicorn 인스턴스로 `curl http://127.0.0.1:8000/api/health` → 200 `{"status":"ok",...}` 확인.
  - **백업·복구 실제 리허설(문서만 쓰고 안 돌려본 게 아님)**: `scripts/backup_db.py` 실행 → `data/backups/tacticore_20260920_112255.db` 생성(1.58MB) → `PRAGMA integrity_check` = `ok` → `analyses`(35)·`users`(5)·`players`(439)·`comments`(0) 행 수가 원본과 전부 일치 → 백업 파일을 별도 경로로 복사해 다시 열어도 정상 조회됨을 확인 후 리허설용 사본은 정리(원본 백업 파일은 `data/backups/`에 그대로 유지, 실제 백업으로도 유효).
  - **미확인**: `flyctl ssh sftp get`으로 프로덕션 DB를 실제로 내려받는 것까지는 이 세션에서 실행하지 않았다(위 배경 참조) — 명령 자체가 실제로 동작하는지는 사용자가 처음 실행할 때 확인이 필요하다.

### 65. 백엔드 pytest 테스트 31개 신설

- **배경**: 개선 로드맵 §5.3(P0). 62/63/64를 연달아 배포하고 나서 사용자에게 남은 P0 중 무엇부터 할지 물었을 때, "지금까지 만든 접근 제어·데이터 로직을 지켜줄 자동 테스트가 하나도 없는 게 가장 큰 리스크"라는 이유로 5.3을 추천했고 사용자가 그대로 선택했다. 이 저장소엔 지금까지 프론트(`frontend/src/**/*.test.ts`, vitest)만 테스트가 있었고 백엔드는 0개였다.

### 66. 요청 제한·세션 보안 강화 + 신고/운영자 처리

- **배경**: 개선 로드맵 §5.5(P0). 65번 다음 우선순위를 물었을 때 "요청 제한·세션 보안 강화(신고/차단 제외)"로 좁혀서 제안했으나, 사용자가 "신고/차단도 이번에 같이"를 선택해 범위가 넓어졌다. **"차단"은 별도의 사용자 간 차단(뮤트) 기능이 아니라 운영자가 신고된 콘텐츠를 숨기거나 지우는 조치로 해석해 구현했다** — 애초 제안 문구가 "report/block + 최소한의 운영자 처리 수단"이었던 데서 이어진 해석이다. 사용자가 "이 사람 글을 안 보고 싶다"는 개인 차단(뮤트)을 의도한 거라면 다른 기능이니 알려달라 — 그건 로드맵 P2 "커뮤니티 운영과 탐색"에 더 가깝다.
- **구현**:
  - **요청 제한(`backend/ratelimit.py`, 신규)**: Redis 없이 프로세스 메모리 슬라이딩 윈도우, IP 기준(Fly-Client-IP 우선, 없으면 X-Forwarded-For의 **오른쪽 끝**만 신뢰 — 왼쪽은 클라이언트가 스푸핑 가능). 회원가입 5회/10분, 로그인 10회/5분, 댓글 작성 20회/분, 댓글 반응·좋아요·신고 각각 30회/분·30회/분·10회/시간. `reset()`을 두고 `conftest.py`의 autouse 픽스처가 매 테스트 전에 호출한다 — TestClient가 모든 요청에 같은 호스트를 쓰는 탓에 리셋 없이는 회원가입이 잦은 테스트에서 실제 로직과 무관한 429가 섞여 들어온다.
  - **세션 보안 강화(`backend/auth.py`, `models.py`)**: `Session.token` 컬럼에 원문 대신 SHA-256 해시를 저장한다(컬럼이 `NOT NULL UNIQUE`라 별도 `token_hash` 컬럼을 추가하는 대신 기존 컬럼 용도를 바꿨다 — advisor 리뷰로 발견, 처음엔 새 컬럼을 추가하려다 테스트 DB에서 즉시 insert 실패했을 문제였다). 해시 전환 이전에 발급된 세션은 자동 무효화된다(재로그인 필요, 허용 가능한 부작용). `expires_at`(30일)·`last_used_at`(5분 이상 지났을 때만 갱신 — 매 요청 쓰기 방지)을 추가했다(`_ensure_column`). 로그인 시점에 그 계정의 만료 세션을 같이 정리한다(`NULL < 만료시각`은 SQL에서 거짓 취급이라 `expires_at IS NULL`도 같이 잡아야 해시 전환 이전 세션도 정리된다).
  - **요청 크기 제한(`backend/schemas.py`, `main.py`)**: `summary` 2000자, `thumbnail` 500KB(base64 기준), `tags` 20개·항목당 30자, `annotations` 국면당 100개, `changing_points` 50개 — 필드별 Pydantic 상한. 그 앞단에 `main.py`의 미들웨어로 `Content-Length` 2MB 초과 요청은 파싱 전에 413으로 거른다.
  - **보안 헤더(`main.py`)**: `X-Content-Type-Options`·`Referrer-Policy`·`X-Frame-Options`만 추가했다. **CSP는 의도적으로 뺐다** — Google Fonts·Vite 빌드 산출물과 충돌 없이 값을 확정하려면 실제 브라우저 검증이 필요한데, 이 세션 환경은 배포된 프로덕션 사이트를 직접 눈으로 확인할 방법이 없다([[shell-sandbox-vs-real-browser-network]]) — 잘못된 CSP를 사람 확인 없이 배포하면 폰트·스크립트 로드가 조용히 깨질 위험이 있다. 미들웨어 등록 순서도 신경 썼다 — CORSMiddleware를 가장 바깥쪽(마지막 등록)에 둬야 위 413 조기 반환 응답에도 CORS 헤더가 실린다(advisor 리뷰로 발견 — 순서가 반대였다면 로컬 개발의 교차 출처 요청에서 413이 CORS 오류로 오인됐을 것).
  - **신고 + 운영자 처리(`backend/models.py`의 `Report`, `backend/routers/moderation.py` 신규)**: 분석·댓글 공통 신고 테이블(같은 사람이 같은 대상을 재신고하면 409). 운영자 판정은 DB 플래그가 아니라 `config.py`의 `admin_emails`(콤마 구분 이메일) 설정값으로 한다 — advisor 리뷰로 "가입 순서상 첫 계정" 방식을 기각했다(테스트마다 등록 순서가 달라 테스트가 우연에 좌우되고, 운영 환경에서도 user id=1이 실제로 누구인지 이 세션에서 확인할 방법이 없다). `models.User.is_admin`은 프로퍼티로 계산해 `UserOut`에 실어 보낸다(프론트가 "신고함" 메뉴 노출 여부만 판단, 실제 권한은 서버가 매 요청 재확인). "차단" 조치는 새 엔드포인트를 만들지 않고 기존 `PATCH .../visibility`·`DELETE /api/comments/{id}`에 운영자 우회 권한만 추가했다 — 같은 동작이 두 경로로 존재하는 걸 피했다.

### 67. Fly.io 콜드 스타트 대응

- **배경**: 개선 로드맵 §5.6(P0 마지막 항목). `min_machines_running = 0`(TO-DO 59) 설정과 프론트의 헬스체크가 충돌하는 문제 — 트래픽이 없으면 Fly 머신이 꺼지고, 다음 요청이 오면 Fly 프록시가 연결을 물고 있다가 머신이 뜨면 응답한다. 이 콜드 스타트 동안 프론트의 헬스체크(`fetchHealth`, 2초 타임아웃)가 먼저 실패하면 저장 버튼이 "서버 미기동"으로 비활성화됐는데, 정작 그 2초는 콜드 스타트가 끝나기엔 너무 짧아 매번 실패했다 — 실제로는 곧 뜰 서버인데도 사용자가 저장을 시도할 방법 자체가 없었다.
- **구현**:
  - **헬스체크 타임아웃 확대 + 제한된 백오프 재시도(`frontend/src/lib/api.ts`의 `fetchHealth`, `frontend/src/hooks/useServerHealth.ts`)**: 타임아웃 2초→8초, react-query `retry: 2`·`retryDelay` 지수 백오프(1.5초→3초, 6초 상한) — 최대 3회 시도. `useServerHealth` 하나를 고치면 이를 쓰는 `SaveButton`·`DuplicateButton`·`RecentAnalyses`·`AnalysesPage`·`CommunityPage`·`VersusPage` 전부 같이 좋아진다. **의도적으로 안 한 것**: 실패 상태에서 주기적으로 자동 재확인(`refetchInterval`)하는 안을 처음엔 넣었다가 advisor 리뷰로 뺐다 — "백엔드가 꺼져 있어도 편집·PNG 내보내기는 동작해야 합니다"가 이 프로젝트의 정식 지원 개발 흐름인데, 그 상태로 화면을 켜 두면 영원히 실패하는 요청을 계속 폴링하게 되는 부작용이 있었다.
  - **저장 버튼이 헬스체크 실패만으로 영구 비활성화되지 않게(`frontend/src/components/editor/SaveButton.tsx`)**: `disabled`에서 `!isServerUp`·`isChecking`을 뺐다 — 이제 비로그인·저장 진행 중일 때만 비활성화된다. 클릭하면 실제 저장 요청이 그대로 나가 Fly 프록시를 거치며 서버를 깨운다. `saveState`(`idle`/`waking`/`saving`/`retrying`/`done`)로 "서버 깨우는 중… → 재시도 중… → 저장 완료" 진행 상태를 보여준다. 저장 요청 자체도 최대 2회 재시도한다 — 단, ApiError(서버가 실제로 응답을 준 4xx/5xx)는 재시도하지 않고 바로 실패로 확정한다(재시도해도 같은 결과라서). ApiError가 아닌 실패(네트워크 단절 등)만 재시도하는데, `apiFetch`가 애초에 클라이언트 타임아웃을 걸지 않는다는 전제(즉 "응답을 못 받았다 = 요청이 서버에 닿지도 못했을 가능성이 높다") 위에 서 있는 안전장치라 코드에 명시해 뒀다 — 나중에 `apiFetch`에 타임아웃이 추가되면 이 가정이 깨지므로 재검토가 필요하다.
  - **`useCurrentUser`도 같은 문제가 있어 같이 고쳤다(`frontend/src/hooks/useAuth.ts`, advisor 리뷰로 발견)**: `/api/auth/me`가 콜드 스타트 중 일시적으로 실패하면 `isLoggedIn`이 false로 굳어버려, 실제로는 로그인 상태인데도 `SaveButton`이 "로그인이 필요합니다"로 막혀버렸다 — 헬스체크 우회는 고쳤지만 인증 체크가 같은 자리에서 다시 막는 셈이라 §5.6의 목표를 달성하지 못했을 문제였다. 401(정상적인 비로그인 상태 — 절대다수의 익명 방문이 여기 해당해 재시도하면 전원이 지연을 겪는다)은 재시도하지 않고, 그 외 실패만 헬스체크와 같은 백오프로 재시도하도록 고쳤다.
- **검증**: 프론트 `tsc -b`(0 errors) / `npm run lint`(0 errors, 기존 경고 3개만) / `npx vitest run`(209개 전부 통과) / `npm run build` 성공. **미확인 — 실제 콜드 스타트 시나리오는 사람이 확인해야 한다**: `min_machines_running = 0`이라 트래픽 없이 몇 분 두면 머신이 자동으로 꺼진다 — 그 상태에서 https://tacticraft.fly.dev 를 새로 열고 편집 후 저장을 눌러, 버튼이 비활성화되지 않고 "서버 깨우는 중… → 저장 완료" 순서로 넘어가는지 확인해달라. 이 세션은 셸에서 띄운 로컬 서버가 실제 브라우저와 네트워크가 분리돼 있어([[shell-sandbox-vs-real-browser-network]]) 이 흐름을 직접 눈으로 본 적 없다.

### 68. 성공/실패 피드백 통일(토스트)

### 71. 모바일 핵심 여정 개선

- **배경**: 개선 로드맵 §6.2(P1 §6 "일상 사용성 개선" 세 번째 항목). 로드맵이 6개 항목을 지목했는데, 구현 전에 실제 코드로 하나씩 확인해보니 이미 된 것과 안 된 것이 섞여 있었다.
  - **실제로 안 되고 있던 것(확인)**: `BottomActionBar.tsx`의 "PNG 내보내기" 버튼이 실제로는 export를 하지 않고 헤더 툴바로 스크롤만 시키고 있었다(주석에 "ShareCard를 두 번 마운트하지 않기 위한 실용적 절충"이라고 명시돼 있었음). `AnalysisList.tsx`(저장 목록)는 반응형 처리가 전혀 없는 `<table>` 하나뿐이었다.
  - **이미 되어 있던 것(확인만)**: "저장 버튼과 썸네일 캡처 상태를 하나의 command/state로 통합한다" — `SaveButton.tsx`의 `handleSave`가 이미 썸네일 캡처와 저장을 한 함수 안에서 처리하고, 하나의 `saveState`(idle/waking/saving/retrying/done, TO-DO 67·68에서 만듦)로 버튼 라벨을 몰아서 관리하고 있었다. 추가 작업 없이 "이미 만족됨"으로 처리.
  - **범위 밖으로 둔 것**: "생성→편집→로그인→저장→공유 모바일 E2E 테스트 추가" — 이 저장소엔 Playwright 같은 E2E 테스트 인프라 자체가 없다(vitest 단위 테스트뿐). 새로 들이는 건 CI 연동 여부까지 같이 걸리는 별도 인프라 결정이라(TO-DO 65가 이미 "CI 연동은 아직 없음"으로 남겨둔 공백과 같은 사안), 이번 스코프에 묶지 않고 따로 논의할 항목으로 남긴다.
- **구현**:
  - **모바일 PNG 내보내기 실제 동작**: `ExportControls.tsx`가 갖고 있던 PNG 쪽 상태(`ratio`·`exporting`·`cardRef`·`handleExport`)를 새 훅 `hooks/useCardExport.ts`로 뽑아 `EditorPage.tsx`가 한 번만 호출하고, `ExportControls`(데스크톱 툴바)와 `BottomActionBar`(모바일 하단 바)에 props로 내려준다 — 캡처 대상 `ShareCard`(화면 밖 `position:absolute`)는 여전히 `ExportControls` 한 곳에만 마운트되므로 이중 마운트 문제는 그대로 피한다. `BottomActionBar`는 이제 "PNG 내보내기"를 누르면 Radix Dialog로 만든 바텀 시트(비율 1:1/4:5 선택 + "PNG 생성" 버튼)가 뜨고, 같은 `handleExport`를 호출해 실제로 파일을 내려받는다.
  - **advisor 리뷰로 발견해 고친 실제 버그**: 바텀 시트의 `handleGenerate`가 처음엔 `await onExport()` 뒤 바로 시트를 닫았는데, `handleExport`는 실패를 삼키지 않고 그대로 던지는 함수라(`finally`로 `exporting`만 되돌림) — export가 실패하면(`html-to-image`가 CORS로 실패할 수 있다는 건 TO-DO 33에서 이미 한 번 실제로 겪은 사례) `setSheetOpen(false)`가 아예 실행되지 않아 시트가 안 닫히고 아무 설명도 없이 멈춘 것처럼 보이는 상태가 됐다. `try/catch/finally`로 감싸 실패 시 토스트 안내 후 시트를 닫도록 고쳤다 — 데스크톱 툴바 버튼은 원래도 실패 시 그냥 라벨만 되돌아가고 에러 안내가 없었는데(PNG 쪽엔 원래 없던 에러 경로), 이번에 모바일 쪽만이라도 토스트로 채웠다.
  - **저장 목록 모바일 카드 레이아웃**: `AnalysisList.tsx`에 카드형 목록(`lg` 미만에서만 보임, `BottomActionBar`와 같은 breakpoint)을 추가 — 썸네일·매치명·홈팀 vs 원정팀·일자·공개 상태(`VISIBILITY_LABELS`, `VisibilitySelect.tsx`의 라벨과 동일)·태그·댓글 링크·삭제 버튼을 한 카드에 담는다. 기존 `<table>`은 `lg` 이상에서만 보이게 `hidden lg:table`로 바꿨을 뿐 그대로 남겼다 — 데이터·삭제 다이얼로그 상태(`pending`)는 두 레이아웃이 공유한다.
  - **사용자 실기기 리포트로 발견해 고친 실제 버그(2026-09-20, 아이폰/아이패드 모바일 Safari)**: 배포 직후 사용자가 "1:1·4:5 둘 다 내보내기가 안 된다, 다운로드/보기 액션시트만 뜨고 실패한다"고 리포트 — `lib/exportImage.ts`의 `exportCard`가 `toPng`(base64 `data:` URL)을 `<a download>`에 그대로 넣고 있었는데, **`data:` URL은 Safari(특히 iOS)에서 `download` 속성이 실제 파일 저장으로 이어지지 않는 잘 알려진 제약**이다 — 증상(액션시트는 뜨지만 둘 다 실패)이 정확히 이 제약과 일치했다. `toBlob`(html-to-image가 직접 제공, base64 왕복 자체를 없앰)으로 바꾸고 `blob:` URL로 다운로드하도록 수정. **advisor 리뷰로 한 번 더 발견한 문제**: 처음 고친 버전은 `URL.createObjectURL` 뒤 `a.click()` 직후 바로 `URL.revokeObjectURL`을 호출했는데, 다운로드는 비동기로 시작되므로 같은 틱에 revoke하면 Safari가 그 레이스에서 특히 잘 져서(아직 안 읽은 blob URL이 무효화됨) 수정이 무효화될 뻔했다 — revoke를 60초 뒤로 미루고, `<a>`를 문서에 붙였다 뗀 뒤 클릭하도록(detached 노드 클릭은 브라우저마다 처리가 다름) 고쳤다. `ExportControls.tsx`의 GIF 다운로드(`downloadBlob`)도 같은 레이스 버그가 있어 같이 고쳤다(GIF 쪽은 사용자가 아직 테스트하지 않아 실제로 겪은 건 아니지만 동일한 버그 패턴).
  - **다운로드 버그 수정, 사용자가 실기기에서 확인함**: 위 다운로드 버그(data: URL → blob: URL)는 배포 후 사용자가 재확인 — 파일 저장 자체는 된다고 확인됨. 이어서 "저장은 되는데 전술판이 안 보여"(제목·날짜·국면·코멘트·벤치 텍스트는 정상)로 다음 문제를 리포트 — **여기서부터는 미해결**, 아래 두 번의 시도 모두 원인을 못 잡았다.
  - **시도 1(실패로 확인됨) — Pitch svg에 명시적 width/height 속성**: advisor가 제시한 가설("피치 svg가 CSS 퍼센트 크기만 갖고 있어, html-to-image가 foreignObject 안에 복제할 때 그 퍼센트가 해석이 안 되면 Safari가 찌부러뜨릴 수 있다") — `Pitch.tsx`에 `ResizeObserver`로 실제 렌더링 크기를 `width`/`height` 속성에 항상 반영하는 안전장치를 추가해 배포(커밋 `c5bea0a`). **사용자 재확인 결과 효과 없음** — advisor도 처음부터 "확정 아님"이라고 명시했던 후보였다.
  - **시도 2(배포했다가 되돌림) — 캡처 직전 피치 SVG를 미리 래스터화**: 더 유력한 원인으로 "html-to-image가 캡처 대상을 `<svg><foreignObject>`에 복제해 넣는데, 캡처 대상 자체가 이미 svg(피치)라 svg 안에 svg가 중첩된다 — 이 중첩 구조를 Safari가 못 그린다"는 가설을 세우고, 캡처 직전에 피치 svg만 `XMLSerializer`→`Image`→`canvas`로 미리 평평한 PNG로 바꿔치기하는 코드(`lib/rasterizeSvg.ts`, `exportImage.ts`의 `prepareCaptureClone`)를 작성해 배포(커밋 `9621c42`). **배포 전에 claude-in-chrome으로 실서비스 ShareCard DOM에 대해 이 로직을 직접 실행해 피치 배경색이 정확히 나오는 것까지 확인**했지만 — 이 검증은 **Chromium**에서 한 것이었다. **사용자 재확인 결과 오히려 악화**: 전엔 파일이 저장되고 텍스트는 보였는데, 이번엔 "보기를 누르면 흰 화면만 보이고, 다운로드 자체가 안 된다"로 후퇴했다. advisor 재검토로 유력한 원인 파악: WebKit(Safari)은 data: URI로 만든 `<img>`가 `onload`를 실제로 다 그릴 수 있는 상태가 되기 전에 미리 쏘는 걸로 알려져 있어 — 이 상태에서 `ctx.drawImage()`가 조용히 아무것도 안 그리고, `canvas.toDataURL()`이 완전 투명 PNG를 내놓고, iOS가 투명 PNG를 흰 배경 위에 미리보기해서 "흰 화면"으로 보였을 가능성이 높다. Chromium은 이 `onload` 타이밍 버그 자체가 없어서 사전 검증이 이 문제를 잡아낼 수 없었다 — **WebKit 전용 버그는 Chromium 사전 검증으로 못 잡는다는 걸 이번에 직접 겪었다.** advisor 권고로 **`git revert 9621c42`로 되돌렸다**(사용자가 마지막으로 확인한 "저장은 됨, 텍스트는 보임, 피치만 안 보임" 상태로 복귀) — 추측성 수정을 더 배포하는 대신, 실제 WebKit 콘솔/화면 수치를 받아올 진단 수단(원격 디버깅 또는 페이지에 진단 정보를 직접 표시하는 디버그 라우트)을 먼저 마련하기로 했다.
  - **진단 도구로 전환 — 사용자에게 Mac이 없어("맥 없음") 임시 디버그 라우트(`/debug/export`, `DebugExportPage.tsx`)를 만들었다**: 실기기 화면에 텍스트로 각 단계 값을 찍어 스크린샷만으로 전달받는 방식. **사용자가 실제 아이폰/아이패드 Safari에서 테스트 1(rasterizeSvg 단독: svg→data URL→Image→decode()→canvas)을 실행한 로그**: 피치 svg 직렬화·`img.decode()` 성공·캔버스 중앙/모서리 픽셀 RGBA가 정확한 피치 배경색(27,94,63,255)으로 나옴 — **이 단계 자체(순수 svg 래스터화)는 실기기 Safari에서 완전히 정상 동작함을 확인**. `rasterizeSvg.ts`를 `img.onload` 대신 `img.decode()` 기반으로 확정.
  - **시도 3(배포했다가 다시 되돌림) — html-to-image 내부 rAF 대기를 직접 구현으로 대체**: 이 세션(claude-in-chrome)에서 진단 페이지의 "전체 캡처 테스트"(html-to-image의 `toBlob`/`toCanvas`까지 실제로 실행)를 Chromium으로 자체 재현하던 중 `toCanvas`가 몇 초 이상 응답 없이 멈추는 걸 발견 — html-to-image 소스(`node_modules/html-to-image/es/util.js`)를 직접 읽어 `createImage`가 `img.decode()` 다음 `requestAnimationFrame` 콜백을 기다리는데 그 콜백이 전혀 호출되지 않는 것으로 특정, `toSvg`(안정적으로 동작 확인됨)까지만 라이브러리를 쓰고 마지막 "이미지 로드→캔버스 그리기" 단계는 rAF 없이 직접 `decode()`만으로 처리하도록 `exportImage.ts`를 재작성해 배포(커밋 `fd4fce8`). **곧바로 자체 발견해 되돌림**: 배포 후 같은 Chromium 환경에서 새 코드(`captureThumbnail`)를 재검증하다가, 캡처는 "성공"으로 끝나지만 **결과 PNG의 모든 픽셀이 완전히 투명한 빈 이미지**라는 걸 발견 — `prepareCaptureClone` 유무와 무관하게 `toSvg`+`decode()`만으로 원본 노드를 그대로 캡처해도 동일하게 빈 이미지가 나오는 것까지 확인해 재현 범위를 좁혔다. 이 시점에 `document.visibilityState`를 직접 찍어보니 `"hidden"`으로 강제되어 있었고(`resize_window`로도 안 바뀜) — **claude-in-chrome 자동화 탭은 `document.visibilityState`가 항상 hidden으로 고정되어 `requestAnimationFrame`이 원천적으로 스로틀링/차단된다는 걸 확인**했다. 즉 애초의 "rAF 콜백이 안 온다"는 재현 자체가 실제 버그가 아니라 **테스트 도구(자동화 탭)의 한계였다** — advisor 재검토로 확정. `git revert fd4fce8`로 되돌리고, 그 위에 `prepareCaptureClone`(피치 svg 평평화)만 다시 적용해 최종 래스터화는 html-to-image의 기본 `toBlob`/`toPng`(rAF 포함)를 그대로 쓰도록 재배포(커밋 `588fb2f` revert + `b4322f7`). **이 변경은 Chromium 자동화로 검증 불가능**(같은 이유로 같은 파이프라인이 자동화 탭에서 신뢰할 수 없게 동작함) — 정적 검증만 통과, 실기기 Safari 재확인 대기 중.
