## 항목 상세

### 31. UI 정리 3건 (회원 탈퇴 이동·역할 칩 제거·선수 선택 링)

- **내용**: "회원탈퇴를 내 정보로 옮기면 좋겠어. 그리고 기본 코멘트 밑에 선수: 역할 은 필요없는거 같아 지우자. 선수 노드를 눌러서 선수수정에 들어갈때 선수 노드 주변에 생기는 검은색흰색 원이 너무 두툼해 다르게 수정해줘" — 서로 무관한 UI 정리 3건을 한 메시지로 요청받아 함께 처리.
- **회원 탈퇴 이동**: `App.tsx`의 `AuthNav`(상단 내비)에 있던 회원 탈퇴 버튼·확인창·뮤테이션 호출을 통째로 `routes/ProfilePage.tsx`로 옮겼다. 내비에는 이메일 링크(내 정보로 이동)·로그아웃만 남는다. 페이지 하단에 `border-t`로 구분한 별도 섹션(destructive 스타일)으로 배치 — 사용자명·비밀번호 변경 폼과 시각적으로 분리해 실수로 누르기 어렵게 했다. `App.tsx`에서 안 쓰게 된 `useWithdraw`·`useNavigate`(AuthNav 로컬)·`closeAnalysis`(AuthNav 로컬) 정리.
- **역할 제안 칩 제거**: `CommentPanel.tsx`의 "+ 이름 · 역할" 칩 목록(전술 역할이 지정된 선수의 역할 설명을 코멘트 끝에 붙여주던 TO-DO 20번 보조 기능)을 통째로 제거. `phasePositions` prop과 `findTacticalRole`/`players` 조회 로직도 같이 정리. `EditorPage.tsx`의 `<CommentPanel>` 호출부에서 `phasePositions` 전달 제거. `TacticalRole.blurb`는 역할 선택 드롭다운(PlayerForm·PlayerEditDialog)의 title 툴팁으로 계속 쓰이므로 `lib/tacticalRoles.ts` 자체는 유지하고 stale해진 doc comment만 갱신.
- **선수 선택 링 개선**: 원인 조사 — 선수 노드(`PlayerNode.tsx`)를 감싸는 `motion.g`가 pan 제스처(`onPan`)를 갖고 있어 Framer Motion이 자동으로 `tabindex="0"`을 붙이는데, 탭하는 순간 그 `<g>`가 브라우저 포커스를 받아 Safari 기본 포커스 아웃라인(두꺼운 이중 테두리)이 그려지고 있었다(Playwright로 `tabindex`/`outline` computed style 직접 확인). 수정: `motion.g`의 인라인 style에 `outline: 'none'`을 추가해 브라우저 기본값을 끄고, `editingPlayerId === player.id`일 때만 보이는 얇은 SVG `<ellipse>` 링(`stroke="hsl(var(--ring))"`, `strokeWidth=0.35`, `fill="none"`, 반지름은 선수 원보다 0.7유닛만 큼)을 새로 추가 — 국면 전환·드래그 애니메이션과 같은 `cx/cy`·`transition`을 공유해 선수를 따라 자연스럽게 움직인다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(174, 회귀 없음)/`npm run build` 통과(CommentPanel의 `phasePositions` prop 제거로 EditorPage 호출부가 타입 에러 없이 컴파일되는 것도 이 단계에서 확인). Playwright로 (1) 감독 프리셋 선택 후 코멘트 패널에 역할 제안 칩이 0개인 것 확인, (2) 선수 노드 클릭 → 다이얼로그가 열린 상태에서 그 노드에 얇은 `--ring` 색 스트로크 링이 그려지고(스크린샷으로 육안 확인) 기본 `outline`은 `none`인 것 확인, (3) 실제 계정을 새로 등록해 로그인 상태로 상단 내비에 "회원 탈퇴" 버튼이 0개, "로그아웃"이 1개인 것 확인, (4) `/profile`로 이메일 링크를 클릭해 클라이언트 라우팅으로 이동한 뒤(직접 URL 이동은 인증 체크 타이밍 이슈로 로그인 화면으로 튕겨서 링크 클릭으로 재확인) 회원 탈퇴 버튼이 1개 있는 것을 스크린샷으로 확인. 검증에 쓴 테스트 계정 2개는 `data/tacticore.db`에서 `PRAGMA foreign_keys = ON` 상태로 직접 삭제해 정리.
- **미확인**: 사용자가 브라우저(가능하면 실기기)에서 세 가지 모두 확인해야 한다 — 특히 선수 선택 링은 이번 세션에서 반복적으로 실기기 전용 버그가 나왔던 영역(Safari 포커스 렌더링)이라 데스크톱 Chromium 검증만으로는 완전히 확신하기 어렵다.

### 32. JSON 내보내기/가져오기(FR-07) 제거

- **내용**: "json내보내기랑 가져오기는 필요할까?" 질문에 답하며, 이 기능이 원래 **백엔드가 꺼져 있어도 작업을 잃지 않게 하는 유일한 안전장치**로 설계됐다는 걸(`CLAUDE.md` — "백엔드가 꺼져 있어도 편집·PNG·JSON 내보내기는 동작해야 합니다", `1단계_요구사항_정의.md` FR-07) 먼저 짚었다. 사용자가 그 설명을 듣고도 "없어도 크게 지장 없으니까 지우자"고 명시적으로 결정해 진행 — 문서화된 기존 결정을 뒤집는 것임을 확인한 뒤 진행한 케이스.
- **구현**: `components/editor/JsonIO.tsx`와 그 전용 헬퍼 `lib/serialize.ts`(다른 곳에서 안 쓰는 것 확인 후) 파일 자체를 삭제. `EditorPage.tsx`에서 `<JsonIO>` 사용·import 제거. `analysisSchema`/`formatZodError`(`lib/schema.ts`)는 프리셋 검증(`loadSample.ts`, `samples.test.ts`)에 여전히 쓰여서 그대로 둠 — JSON I/O 전용이 아니었다.
  - **문구 갱신**: `SaveButton.tsx`의 "서버 미기동/로그인 필요 — 편집·PNG·JSON은 계속 사용 가능합니다" 안내 두 곳, `useServerHealth.ts`의 doc comment에서 "·JSON" 언급 제거.
  - **`CLAUDE.md` 갱신**: "현재 상태" 목록에서 "JSON 입출력" 빼고 제거 사실을 괄호로 기록, "백엔드가 꺼져 있어도 ... 동작해야 합니다" 결정 사항에서 JSON 부분을 빼고 제거 사실을 괄호로 기록 — 이 문서는 "현재 저장소 상태"를 안내하는 살아있는 문서라 최신 상태로 맞췄다.

### 33. GIF 내보내기가 끝없이 "만드는 중"에 멈추는 버그 수정

- **내용**: "gif내보내기 했는데 계속 만드는 중 이야" 리포트. Playwright로 그대로 재현 — 버튼이 "GIF 만드는 중…"에서 30초 넘게 안 바뀌었다(이전 세션과 달리 이번엔 데스크톱 Chromium에서도 100% 재현되는 버그였다).
- **원인**: 콘솔에 프레임마다 반복되는 에러 쌍을 확인했다 — `html-to-image`의 `toCanvas`가 캡처할 때마다 `embedWebFonts` 단계에서 문서의 모든 스타일시트의 `cssRules`를 읽으려 시도하는데, `index.html`에 Hallmark 리디자인(2026-09-11, 29번 항목) 때 추가한 Google Fonts `<link rel="stylesheet" href="https://fonts.googleapis.com/...">`가 **cross-origin**이라 `cssRules` 접근 자체가 브라우저 CORS 정책으로 막혀 `SecurityError: Failed to read the 'cssRules' property`가 매번 발생했다. GIF는 39프레임(`buildGifFrameSpecs`: 국면 3개 × (정지 1장 + 전환 보간 12장))을 순서대로 캡처하는데, 이 실패한 시도 하나가 프레임당 약 2초를 잡아먹어 **39장 전체가 70초 넘게 걸렸다** — "끝없이 멈춘" 게 아니라 극도로 느려진 것. PNG 내보내기(1회 캡처)는 같은 에러를 조용히 한 번만 겪고 넘어가서 눈에 안 띄었을 뿐 똑같이 느려지고 있었다.
- **수정**: `html-to-image`의 `toCanvas`/`toPng` 호출 3곳(`GifExportRunner.tsx`, `lib/exportImage.ts`의 `exportCard`·`captureThumbnail`) 전부에 `skipFonts: true` 옵션 추가 — 캡처는 이미 `document.fonts.ready`로 폰트가 로드·페인트된 같은 브라우저 탭 안에서 일어나므로, html-to-image가 폰트를 별도로 재다운로드해 SVG에 base64로 embed할 필요가 없다(embed는 SVG 마크업을 이 탭 밖에서 독립적으로 쓸 때만 의미가 있음). 이 단계를 건너뛰면 CORS 에러 자체가 안 나고, 시각적 결과물(이미 렌더링된 폰트 그대로 캡처)도 동일하다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(174, 회귀 없음)/`npm run build` 통과. Playwright로 GIF 내보내기 재현 — 수정 전 30초 관찰 동안 한 번도 안 끝나던 게, 수정 후 **4초 만에** 버튼이 "GIF 내보내기"로 돌아오고 다운로드가 트리거됨을 확인, 콘솔에 CORS `SecurityError`가 더 이상 안 뜨는 것도 확인.
- **추가 확인**: Playwright로 실제 다운로드된 GIF 파일을 저장해 육안으로 열어봄 — 제목이 Nanum Gothic Coding, 본문이 IBM Plex Sans KR로 정상 렌더링되고 폰트 폴백으로 인한 간격 깨짐(이전 세션에서 잡았던 버그) 없이 나온 것을 확인. GIF 전체 재생(프레임 간 애니메이션)까지는 정적 이미지 뷰어로 확인이 안 돼 이 부분만 사용자 확인이 남는다.
- **미확인**: 여러 프레임에 걸친 실제 재생(모프 애니메이션이 자연스럽게 이어지는지)은 GIF를 재생 가능한 뷰어로 열어야 확인되므로 사용자가 봐줘야 한다.

### 35. 전술 대결 패스 공 반복 재생

- **내용**: "전술 대결에서 패스길에 공이 계속 움직이면 좋겠어. 지금은 한번만 움직여." `AnnotationLayer.tsx`의 `PassChainBall`은 2026-09-10에 이미 한 번 논의된 이력이 있었다 — 당시 `repeat: Infinity`(계속 왕복)였던 걸 "한 번만 움직이고 도착점에 멈춤"으로 바꾼 게 그날의 결정이었다. 이번 요청은 사실상 그 결정을 정면으로 뒤집는 것처럼 보여서, 먼저 그 결정의 배경(편집기 도크스트링)을 확인했다.
- **문서화된 기존 결정과의 충돌 확인**: 2026-09-10 결정의 실제 이유는 두 가지 다 **편집기(EditorPage)에서만 나는 어긋남**이었다 — (1) 드리블(carry) 구간에서 선수는 한 번만 모프하고 멈추는데 공만 계속 왕복해 "선수는 도착했는데 공이 또 움직인다", (2) 병합된 시점을 스텝별로 재생할 때 각 스텝 사이 정지 구간(0.6~1.8초) 동안 선수는 이미 멈춰 있는데 공만 계속 왕복해 "선수는 가만있고 공만 움직인다". 전술 대결 뷰(`MatchupView`)의 선수 노드(`StaticPlayerNode`)는 두 분석의 **고정 스냅샷**이라 애초에 모프도 안 하고 시점 스텝 재생 기능도 없다 — 즉 2026-09-10에 문제였던 두 어긋남 자체가 이 컨텍스트에서는 구조적으로 일어날 수 없다. 그래서 "무조건 한 번만 재생"이 아니라 **컨텍스트별로 다르게** 가는 게 맞다고 판단해, 기존 결정을 지우는 대신 새 옵션으로 확장했다.

### 39. 전술 대결 뷰 글자 왜곡 수정(피치 CSS 버그) + 폰트 통일

- **내용**: "선수이름들이 너무 가로로 펼쳐진 느낌이야 좀 더 자연스럽게 수정해주고 압박라인 글자로 폰트 우리지금 쓰고있는거로 수정해줘. 그냥 이 사이트에 모든 글자를 지금 우리가 쓰는 폰트로 수정해줘." 처음엔 "폰트가 다르다"는 요청으로 읽었는데, 조사해보니 실제 원인은 두 가지가 섞여 있었다 — (1) 일부 SVG `<text>`에 `PITCH_TEXT_FONT_FAMILY`가 빠져 있던 것(진짜 폰트 문제), (2) `/versus` 피치 컨테이너가 의도한 가로세로 비율을 못 맞추고 찌그러져서 그 위의 모든 글자·마커가 가로로 늘어나 보이던 것(CSS 레이아웃 버그, 폰트와 무관).
- **1) 폰트 통일(전수 조사)**: `<text>`/`<motion.text>`가 있는 파일 전부(12개, false positive 제외 9개 실사용) 조사. `PressingLine`·`MatchupOverloadLayer`·`OverloadLayer`·`CompactnessBox`·`AnnotationLayer`(삭제 배지 "✕") 5곳에 `PITCH_TEXT_FONT_FAMILY`가 빠져 있어 추가. `PlayerNode`·`PrintPlayerNode`·`SharePlayerNode`·`StaticPlayerNode`는 34번에서 이미 처리돼 있었다.
- **2) 피치 CSS 버그 — 실제 근본 원인**: `Pitch.tsx`의 컨테이너 div가 landscape든 portrait든 `aspect-[…] h-full max-h-full w-full max-w-full`을 동시에 갖고 있었다 — `h-full`과 `w-full`을 **동시에** 주면 두 축 다 "이미 정해진 값"이 되어 `aspect-ratio`가 개입할 자리가 없어져 **완전히 무시된다**(CSS 스펙상 aspect-ratio는 두 치수 중 하나가 auto일 때만 나머지를 계산해준다). 그 결과 `/versus`의 `flex h-full flex-col` 안에서 `AdvantageBadge`·`KeyZoneCallout`·`TacticalSuggestions`처럼 고정 높이 패널이 늘어날 때마다 피치의 `flex-1` 몫 높이가 줄어드는데, 너비는 여전히 `w-full`이 강제해서 **피치 자체가 옆으로 찌그러졌다** — 그 위에 그려지는 모든 것(선수 마커 원, 글자, 구역 박스)이 같이 눌렸다.
- **잘못 짚었던 첫 시도**: 처음엔 "SVG `viewBox`가 `preserveAspectRatio="none"`으로 비균일 스케일되니까 `<text>`만 별도로 보정해야 한다"고 판단해 `StaticPlayerNode`·`PressingLine`·`MatchupOverloadLayer`에 `scale(LANDSCAPE_TEXT_X_SCALE, 1)` 보정 `<g>`를 추가했다(이론상 맞는 접근 — `circularRadius`/`swapForLandscape`가 도형에 대해 이미 하고 있는 걸 글자에도 하는 것). 그런데 advisor 상담에서 "마커 원이 진짜 원으로 보이는지부터 재보라"는 지적을 받고 `getBoundingClientRect()`로 실측했더니 `markerPxRatio`가 1이 아니라 3.1까지 나왔다 — 처음엔 이것도 컨테이너가 심하게 찌그러진 증거로 오판했는데, 다시 보니 셀렉터가 선수 마커가 아니라 **패스 공 애니메이션 원**(`AnnotationLayer`의 `BALL_RADIUS`, landscape 보정이 아예 없는 별개의 기존 버그)을 잘못 집은 것이었다. `rx`/`ry` 속성값으로 정확히 선수 마커만 골라 다시 재보니 실제 왜곡은 (내가 이번 세션에 추가한 패널들 때문에) 최대 1.3배 정도였다 — text-only 보정으로는 이 컨테이너 자체의 찌그러짐을 못 고친다는 걸 이 시점에 확인.
- **최종 수정**: `Pitch.tsx`의 landscape 분기에서만 `w-full`을 뺐다(`'mx-auto aspect-[105/68] h-full max-h-full max-w-full'`) — 높이(`h-full`)만 정해진 값으로 남기니 `aspect-ratio`가 그 높이에 맞는 너비를 정상적으로 계산하고, `max-w-full`은 화면이 아주 넓을 때의 상한선으로만 작동한다. portrait 분기는 그대로 뒀다(MVP 때부터 사용자가 계속 확인해 온 기준선이라 이번 요청 범위 밖). 이 CSS 수정 하나로 마커 원의 `getBoundingClientRect()` 가로:세로 비율이 정확히 **1.0**이 됐다 — 1)에서 추가한 텍스트 보정 `<g transform="scale(…)">`은 그대로 유지했는데, 컨테이너가 이제 정확한 비율로 렌더링되니 그 보정의 전제(텍스트만 별도로 비균일 축소가 필요하다는 것 — 도형은 `circularRadius`가 이미 보정하지만 `<text>`는 아무 보정이 없었다는 점)가 유효해져서 글자도 같이 자연스러워졌다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(177, 회귀 없음)/`npm run build` 통과. Playwright로 (1) 선수 마커 원의 `getBoundingClientRect()` 너비:높이가 1.0(완벽한 원)인 것을 CSS 수정 전후로 비교 확인(수정 전 1.3, 수정 후 1.0), (2) 1400×1000·900×800 두 뷰포트 스크린샷으로 피치·펜alty 박스·센터서클이 찌그러지지 않고 제대로 된 축구장 비율로 보이는 것, (3) 선수 이름표·번호·압박 라인 문구가 가로로 안 퍼지고 자연스러운 글자 비율로 보이는 것을 육안 확인. `<Pitch orientation="landscape">`는 코드베이스 전체에서 `MatchupView.tsx` 한 곳에서만 쓰여서(grep으로 확인) 이 CSS 변경의 영향 범위가 `/versus` 하나로 한정된다는 것도 확인.
- **교훈(기록해둘 것)**: 처음엔 "패스 공 원의 왜곡이 3배"라는 잘못된 측정치 때문에 "내가 오늘 추가한 패널들이 심각하게 컨테이너를 찌그러뜨렸다"고 과잉 진단할 뻔했다 — 실제로는 셀렉터가 다른 도형(패스 공)을 집은 계측 오류였다. `rx`/`ry` 등 **알려진 입력값과 대조해서 어떤 요소를 재고 있는지 먼저 확인**하지 않으면, 스크린샷도 숫자도 둘 다 그럴듯해 보이는 잘못된 결론에 도달할 수 있다.
- **미확인**: 사용자가 브라우저에서 시작 화면이 아니라 실제 `/versus` 화면을 열어 선수 이름표·압박 라인 글자가 "자연스러워" 보이는지, 피치 비율 자체가 정상적인 축구장처럼 보이는지 확인해야 한다.

Playwright로 과르디올라 vs 아르테타 조합을 띄워 (1) 3칸의 `title` 속성(왼쪽 2:2·중앙 0:1·오른쪽 2:1)을 DOM에서 읽어 셋을 더하면 전체 배지의 "4구역:4구역"과 정확히 일치하는 것(2+0+2=4, 2+1+1=4)을 확인해 구역이 어느 쪽에도 중복·누락 없이 정확히 3등분됐다는 것을 검증, (2) 스크린샷으로 게이지 바 3개가 기존 전체 게이지 바와 같은 스타일로 자연스럽게 이어져 보이는 것 확인.

### 41. 전술 대결(/versus) PNG 카드 내보내기

- **내용**: "더 추가할 기능들은 없을지 너가 찾아줘" 요청에 요구사항 문서·TO-DO 히스토리·기각 기록·현재 코드를 훑어 4가지를 제안했고(전술 대결 내보내기·커뮤니티 좋아요·PWA·매치업 조합 저장/북마크), 사용자가 "전술 대결 PNG/카드 내보내기(추천)"와 "커뮤니티 좋아요/인기순 정렬"을 골랐다(PWA는 "다른 2개만 먼저"로 보류). 에디터는 PNG/GIF 내보내기(FR-05)가 있는데 이번 세션에 배지·키포인트·게이지 바까지 공들여 만든 `/versus`는 내보내기가 전혀 없던 게 가장 확실한 공백이었다.

- **카드 구현**: 에디터의 `SharePngCard`와 같은 원칙(화면을 그대로 캡처하지 않고 고정 1080px 폭 카드를 별도 렌더링해서 캡처)으로 `VersusShareCard.tsx`를 만들었다. `VersusPage.tsx`에 비율(1:1/4:5) 선택 + "PNG 내보내기" 버튼을 추가하고 기존 `lib/exportImage.ts`의 `exportCard`를 그대로 재사용했다(에디터 전용 로직처럼 보였지만 실제로는 `useAnalysisStore`의 `isMorphing` 플래그만 체크하는데 대결 뷰는 그 플래그를 안 써서 항상 false — 그대로 재사용해도 안전).
- **버그 발견 및 수정(html-to-image 캡처 특유의 문제)**: 처음엔 `AdvantageBadge`·`ZoneSideGauges`·`KeyZoneCallout`(화면용 Tailwind flex 컴포넌트)을 그대로 재사용했는데, 실제 PNG로 내보내 보니 팀명+우세 구역 수 텍스트가 줄바꿈되면서 그 아래 게이지 바와 겹쳐 보이는 문제가 있었다. Playwright로 (1) 같은 오프스크린 카드 엘리먼트를 `locator.screenshot()`으로 직접 캡처(실제 DOM, html-to-image 안 거침)한 결과와 (2) 실제 `PNG 내보내기` 버튼으로 받은 `toPng()` 결과물을 나란히 비교했더니, (1)은 줄바꿈 없이 정상인데 (2)만 깨져 있었다 — `html-to-image`가 캡처 시 내부적으로 SVG `foreignObject`를 거치는데, 그 경유 렌더링에서 `justify-between` flex 배치의 텍스트 폭 계산이 실제 브라우저 레이아웃과 다르게 나온 것으로 보인다. `SharePngCard`가 처음부터 Tailwind 없이 인라인 스타일만 쓰는 이유가 아마 같은 문제였을 것으로 추정 — 화면용 컴포넌트를 재사용하는 대신 같은 숫자(`computeMatchupData`/`computeSideAdvantage`)를 인라인 스타일로 직접 그리는 쪽으로 바꿔서 해결했다.
- **범위에서 뺀 것**: `TacticalSuggestions`(전술 개선방안 문단)는 카드에 안 넣었다 — 공유용 카드는 한눈에 훑는 용도라 문장형 조언까지 넣으면 정보가 과하다고 판단(SharePngCard가 코멘트를 500자로 자르는 것과 같은 절제).
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(183, `matchup.test.ts` 4건 포함, 회귀 없음)/`npm run build` 통과. Playwright로 실제 "PNG 내보내기" 버튼을 눌러 다운로드까지 끝까지 실행(파일 크기 404KB, 정상 크기)하고 스크린샷으로 텍스트 줄바꿈·겹침이 없는 것, 팀명·공수 표시·전체 게이지·3구역 게이지·피치·키포인트 배지가 모두 담긴 것을 육안 확인.
- **미확인**: 사용자가 실제로 내보낸 PNG 파일을 열어 공유하기 좋은 형태인지(비율·정보량·가독성) 확인해야 한다.

### 42. 커뮤니티 좋아요 + 인기순 정렬

- **내용**: "더 추가할 기능들은 없을지 찾아달라"는 요청에서 41번과 함께 골랐다 — "댓글은 있는데 좋아요·인기순 정렬이 없어서 최신순 말고는 정렬 기준이 없다"는 공백.
- **백엔드**: 새 `Like` 모델(`analysis_id`+`user_id` 유니크 제약, `Comment`와 같은 이유로 `create_all`이 새 테이블을 자동 생성 — ALTER TABLE 불필요) + `crud.toggle_like`(이미 좋아요 상태면 행 삭제=취소, 아니면 생성=좋아요, 1인 1회는 유니크 제약이 보장). `crud.list_public_analyses`에 좋아요 수·"내가 눌렀는지"를 댓글 수와 같은 방식(분석 id 목록으로 GROUP BY 집계 후 파이썬에서 합침)으로 추가하고, `sort=popular`일 때는 좋아요 수가 SQL 컬럼이 아니라 이렇게 집계한 값이라 DB `order_by` 대신 이미 최신순으로 가져온 파이썬 리스트를 `list.sort`(안정 정렬)로 다시 정렬해 좋아요 수가 같으면 최신순이 2차 정렬 기준이 되게 했다. `POST /api/community/analyses/{id}/like`는 댓글 작성과 같은 이유로 로그인 필수(`auth.get_current_user`), 목록 조회는 `get_current_user_optional`로 비로그인도 보되 "내가 눌렀는지"만 로그인 시에만 채운다.
- **프론트**: `CommunityPage.tsx`에 최신순/인기순 정렬 칩(저장 목록의 그룹 칩과 같은 스타일) + 카드마다 하트 버튼(눌렀으면 채워진 빨간 하트). 하트 버튼이 카드 전체를 감싸는 `<Link>` 안에 있어서 클릭 시 `preventDefault`+`stopPropagation`으로 페이지 이동을 막았다. 비로그인 상태에서 누르면 `/login`으로 이동(댓글 작성 폼과 다르게 이 앱엔 아직 "로그인 필요" 토스트가 없어서, 저장 목록 페이지가 비로그인 시 보여주는 로그인 안내 링크와 같은 맥락으로 바로 로그인 페이지로 보내는 쪽을 택함). 좋아요 토글 성공 시 정렬 무관 커뮤니티 쿼리 전체를 무효화한다 — 인기순 정렬 중엔 좋아요 개수 변화로 순서 자체가 바뀔 수 있어 부분 갱신 대신 다시 불러오는 쪽이 안전하다고 판단.
- **실수·수정**: 백엔드 코드를 다 고친 뒤 curl로 확인했는데 새 `/like` 라우트가 응답에 없고 `likes` 테이블도 안 생겨 있었다 — `uvicorn --reload`가 떠 있던 기존 프로세스가 파일 변경을 못 감지한 상태였다(Windows에서 `taskkill`/`netstat`의 PID 정보가 서로 어긋나 보여 처음엔 혼란스러웠는데, PowerShell `Get-Process`/`Stop-Process`로 실제 프로세스를 확인해 정리했다). 백엔드 프로세스를 완전히 새로 띄운 뒤에야 새 라우트·테이블이 반영된 것을 확인 — 이후 검증은 전부 이 새 프로세스 기준으로 다시 진행했다.
- **검증**: `tsc -b`/`npm run lint`(0 errors)/`vitest run`(183, 회귀 없음)/`npm run build` 통과. curl로 (1) `likes` 테이블이 실제로 생성된 것, (2) 비로그인 `POST /like`가 401을 돌려주는 것을 확인. Playwright로 실제 로그인 계정으로 (1) 좋아요를 누르면 하트가 채워지고 카운트가 0→1로 바뀌는 것, (2) 다시 누르면 1→0으로 취소되는 것, (3) 클릭해도 `/community`에서 페이지 이동이 안 일어나는 것(부모 `<Link>` 전파 차단 확인), (4) 인기순으로 정렬을 바꿔도 좋아요 상태(채워진 하트)가 그대로 유지되는 것, (5) 비로그인 상태에서 좋아요를 누르면 `/login`으로 이동하는 것을 확인. 스크린샷으로 좋아요 1개인 카드가 인기순에서 맨 앞에 오는 것도 확인.
- **미확인**: 사용자가 브라우저에서 실제로 다른 계정으로 좋아요를 눌러보고, 커뮤니티 목록에서 정렬·하트 표시가 기대한 대로 보이는지 확인해야 한다.

### 43. 전술 대결 왼쪽/오른쪽 기준 안내 문구

- **내용**: "왼쪽 오른쪽 중앙이 공격팀 기준이잖아. 근데 눈에 바로 볼때는 좀 헷갈려. 기준을 적어두는게 좋겠어" — 40번에서 만든 왼쪽/중앙/오른쪽 3구역 게이지 바(그리고 같은 `CHANNEL_KOREAN` 어휘를 쓰는 `AdvantageBadge`·`KeyZoneCallout`·`TacticalSuggestions`)에 "이 좌우가 누구 기준인지"를 적어달라는 요청.
- **전제 검증 결과(사용자 확인 전 먼저 정정 필요)**: 사용자는 "공격팀 기준"이라고 알고 있었지만, `lib/matchup.ts`의 `computeMatchupData`를 다시 읽어보니 실제로는 **항상 `전술 A(채움)`팀 기준**이고 "공수 교대"(누가 공격인지) 토글과는 무관했다 — `syntheticPhase.positions`가 항상 `dataA.positions`(전술 A 자신의 좌표, 국면과 무관하게 A 자신의 공격 방향 기준 그대로)이고, `dataB`만 `mirrorPoint`로 A 프레임에 맞춰 미러링될 뿐 채널 축의 기준 자체는 바뀌지 않는다. 거기에 더해 Playwright로 실제 랜드스케이프 화면에서 선수 좌표를 픽셀로 읽어보니, 채널(왼쪽/오른쪽) 축은 화면의 좌우가 아니라 **위아래**로 그려지고 있었다(`transposePoint`가 데이터 x축→화면 y축으로 옮기기 때문 — 화면 좌우는 대신 서드(전진 방향) 축이 차지한다). 즉 "왼쪽/오른쪽"은 (1) 공격팀이 아니라 전술 A 고정이고, (2) 화면에서도 좌우가 아니라 위아래로 나타난다 — 사용자가 느낀 "헷갈림"의 실제 원인은 이 두 가지였다.
- **구현**: `ZoneSideGauges.tsx`의 3구역 게이지 바 아래에 작은 안내 문구 한 줄을 추가했다 — "왼쪽·오른쪽은 {전술 A 팀명} 공격 방향 기준(공수 교대와 무관) · 가로 화면에서는 위아래로 표시됩니다". `AdvantageBadge`·`KeyZoneCallout`·`TacticalSuggestions`는 같은 `CHANNEL_KOREAN` 어휘를 문장 속에서만 쓰고 별도 축 라벨이 없어서 반복 표기하지 않았다(사용자가 실제로 가리킨 "이렇게" 게이지 바 하나로 범위를 좁힘). `VersusShareCard.tsx`는 `ZoneSideGauges`를 재사용하지 않고 인라인 스타일로 3구역 게이지를 따로 그리므로(TO-DO 41의 html-to-image 버그 회피 때문), 같은 문구를 인라인 스타일로 별도 추가했다 — PNG로 내보낸 카드는 화면 밖에서도 혼자 돌아다니므로 원본 페이지의 설명 없이도 뜻이 통해야 한다.
- **검증**: `tsc -b`/`npm run lint`(0 errors, 기존 warning 3건만)/`npx vitest run`(183, 회귀 없음). Playwright로 실제 화면에서 (1) 랜드스케이프 피치의 채널 경계선이 위아래로 5줄 나뉘는 것을 스크린샷으로 재확인(위 전제 검증에서 쓴 것과 같은 조합), (2) `ZoneSideGauges` 아래 안내 문구가 실제로 렌더링되는 것, (3) 화면 밖 `VersusShareCard`에도 같은 문구가 존재하는 것(`text=가로 화면에서는 위아래로 표시됩니다`가 페이지에 2개 — 화면용 1개 + 카드용 1개)을 확인.
- **미확인**: 사용자가 문구가 실제로 헷갈림을 해소하는지, 문구 위치·문구 자체(예: "위아래로 표시됩니다"라는 표현이 직관적인지)가 괜찮은지 확인해야 한다.

### 44. 전술판 위 L/C/R 구역 라벨

- **내용**: "전술판에 오른쪽 중앙 왼쪽을 표현하는게 좋을거같아. 짧게 L, R로 표현하자" — 43번의 문구는 글로 설명만 할 뿐 피치 위 어디가 "왼쪽"인지는 여전히 눈으로 찾아야 했다. 짧은 글자(L/R, 그리고 중앙 C)를 피치 위에 직접 찍어달라는 요청.
- **구현**: `ChannelGrid.tsx`에 `sideLabels?: boolean`(기본 false) prop을 추가했다. 왼쪽(leftWing+leftHalf)·중앙(center)·오른쪽(rightHalf+rightWing) 3묶음 — `versusAdvantage.ts`의 `SIDE_CHANNELS`(게이지 바가 쓰는 것과 같은 묶음, 다만 순환 참조를 피하려고 여기선 별도로 `CHANNEL_BOUNDS`에서 직접 계산) — 각 구간 중앙에 L/C/R 한 글자를 그린다. 라벨 위치는 데이터 좌표 `{x: 구간중앙, y: 30}`을 `transposePoint`로 옮겨서 정하는데, y=30을 고른 이유는 페널티 박스 깊이(~15.7, 실측으로 박스가 중앙 채널 쪽으로 폭넓게 걸쳐 있는 걸 계산해 확인)를 벗어나면서 `MatchupOverloadLayer`의 서드별 "3:0" 구역 숫자가 앉는 서드 중심(16.65/50/83.35)과도 안 겹치는 자리이기 때문 — 두 레이어가 기본값으로 항상 같이 켜져 있어(`showOverload`·`showChannelGrid` 둘 다 기본 true) 겹침을 실제로 신경 써야 했다. 글자 렌더링은 `MatchupOverloadLayer`의 가로 왜곡 보정(`LANDSCAPE_TEXT_X_SCALE` + `scale(x,1)` 트릭, TO-DO 39)과 외곽선(`paintOrder: stroke`) 패턴을 그대로 재사용했다. `sideLabels`는 `MatchupView.tsx`와 `VersusShareCard.tsx`(전술 대결의 실시간 화면과 PNG 카드, 둘 다 `orientation="landscape"`)에서만 켰다 — 에디터·공유 카드(portrait)는 x축이 이미 화면 좌우와 일치해 헷갈릴 일이 없으므로 그대로 뒀다(범위를 43번과 같은 "전술 대결"로 좁힘).
- **검증**: `tsc -b`/`npm run lint`(0 errors, 기존 warning 3건만)/`npx vitest run`(183, 회귀 없음). Playwright로 과르디올라 vs 아르테타 조합을 띄워 스크린샷으로 (1) L이 위쪽 밴드, C가 중앙 밴드, R이 아래쪽 밴드에 자리한 것(43번에서 확인한 "위아래로 표시된다"는 문구와 일치), (2) 글자가 가로로 눌리거나 늘어나지 않고 정비율로 보이는 것, (3) 페널티 박스나 "3:0" 구역 숫자와 겹치지 않고 읽을 수 있는 자리에 있는 것을 확인.
- **미확인**: 사용자가 브라우저에서 L/C/R 글자가 실제로 헷갈림을 줄여주는지, 위치·크기·색이 적당한지 확인해야 한다.

### 45. 위협 가중 구역 점수

- **내용**: 안첼로티 브라질(A) vs 이정효 수원삼성(B) 대결(A 공격×B 수비)에서 왼쪽/중앙 게이지가 둘 다 "1:1 동률"로 나온 걸 사용자가 이해 못 해서, 세션이 실제 두 프리셋의 attack/defense 좌표를 손으로 대조해 원인을 설명했다 — 왼쪽·중앙 모두 "각 팀이 딴 구역 1개씩" 상쇄된 결과였는데, 브라질의 우위 2곳은 전부 자기 진영(하프스페이스·중앙 각각 defensive 서드)이고 수원의 우위 2곳은 중원·**브라질 박스 바로 앞 중앙**(attacking 서드)이라 같은 "1구역"이어도 실제 위험도는 전혀 달랐다. 이어서 "보통 그렇게 상쇄시키나? 다른 사이트들도 그런지 찾아봐" → 세션이 웹 검색(Expected Threat, Pitch Control/Voronoi, 히트맵)을 조사한 결과 실제 분석 도구들은 세부 구역 결과를 합산해서 하나의 승패 카운트로 뭉개지 않는다는 걸 확인 → "전술대결에 더 좋은 기능 추천해줘"에 세션이 4개(①위협 가중 점수 ②고립 매치업 탐지 ③무게중심/쏠림 지수 ④팀 폭/깊이 비교, 실용성·구현 난이도 순) 제안 → 사용자가 "우선순위대로 진행시켜줘, 실용성이 가장 중요해"로 확정. 1번만 이번에 구현했다(상세 이유는 위 43/44 앞 문단 참조).
- **원칙 확인(구현 전)**: `versusAdvantage.ts` 파일 상단 docstring에 이미 "가짜 확률/예측 금지"(TO-DO 16/22) 원칙이 적혀 있어, 가중치를 얹은 점수가 이 원칙에 걸리는지부터 짚었다 — 이 원칙은 "실제 시뮬레이션 없이 승률/점유율처럼 보이는 숫자를 만들지 말라"는 것이고, 위협 가중 점수는 지금 그려진 좌표의 15구역 own/opp 차이(`computeOverload`가 이미 내는 사실)에 고정된 가중치 표를 곱한 합산치일 뿐 확률이 아니다 — %나 소수 확률처럼 안 보이게 "가중 점수"라는 이름과 소수 첫째 자리까지만 반올림해서 표기해 구분했다.
- **구현**: `lib/zones.ts`에 `CHANNEL_THREAT_WEIGHT`(wing 0.6 · half 1 · center 1.4, 좌우 대칭)·`THIRD_THREAT_WEIGHT`(attacking 3 · middle 1 · defensive 0.3)와 이 둘을 곱하는 `zoneThreatWeight(channel, third)`를 추가했다 — 실제 이벤트 데이터로 학습한 xT 모델이 아니라 "중앙·상대 진영에 가까울수록 위험하다"는 축구 상식을 고정값으로 반영한 것이라고 주석에 명시했다. `versusAdvantage.ts`에 `computeThreatWeightedScore(zones)`를 추가 — 15구역 각각의 diff에 가중치를 곱해 A/B로 나눠 합산한다(동률 구역은 원래도 diff=0이라 기여 없음). `AdvantageBadge.tsx`(전체 요약 배지, `ZoneSideGauges` 바로 위)에 기존 "N구역 우세" 막대·문장은 그대로 두고 그 아래 한 줄만 추가했다 — "위협 가중 점수(중앙·상대 진영에 가까울수록 가중치 큼): 브라질 1 · 수원삼성 9.4"처럼, 기존 숫자를 대체하지 않고 나란히 보여줘야 사용자가 새 점수가 어디서 나왔는지 기존 구역 숫자와 대조해 검증할 수 있다.
- **범위에서 뺀 것**: 4개 제안 중 1번만 구현했다 — 이미 AdvantageBadge·ZoneSideGauges·안내 문구·KeyZoneCallout·TacticalSuggestions·피치까지 쌓여 있는 화면에 요약 패널을 한꺼번에 더 얹으면, 43/44번에서 막 해결한 "정보가 많아서 헷갈린다"를 다시 만들 위험이 있다고 판단해 나머지 3개(고립 매치업·무게중심·폭 깊이 비교)는 사용자가 이번 걸 써 보고 판단한 뒤 순서대로 진행하기로 했다. `VersusShareCard.tsx`(PNG 내보내기 카드)에도 아직 반영 안 했다 — TO-DO 41이 "카드는 한눈에 훑는 용도라 정보 과다 방지"로 `TacticalSuggestions`를 뺀 것과 같은 이유로, 사용자가 화면에서 이 점수가 쓸모 있다고 확인한 뒤 카드에도 넣을지 정하는 게 순서에 맞다고 봤다.
- **검증**: `tsc -b`/`npm run lint`(0 errors, 기존 warning 3건만)/`npx vitest run`(186, 신규 3건 포함, 회귀 없음) 통과. 신규 유닛 테스트가 이 기능이 실제로 필요한 이유를 그대로 회귀 가드로 남긴다 — (1) 위 안첼로티/수원 4구역을 그대로 넣으면 단순 개수로는 2:2 동률이지만 가중 점수는 수원 쪽이 더 크다는 것, (2) 동률만 있으면 0:0을 반환하는 것, (3) `leftWing`/`rightWing`·`leftHalf`/`rightHalf`가 정확히 같은 가중치를 받아 이 점수 자체엔 좌우 편향이 없다는 것. Playwright로 실제 안첼로티 vs 이정효 수원삼성 조합을 띄워 스크린샷으로 "브라질 2구역 우세...수원삼성 2구역 우세"(기존 표시, 그대로 유지) 바로 아래 "위협 가중 점수: 브라질 1 · 수원삼성 블루윙즈 9.4"가 렌더링되는 것을 확인 — 손 계산·유닛 테스트·실제 화면 세 군데서 같은 결론(수원 쪽이 훨씬 위협적)이 나오는 것까지 확인했다.
- **미확인**: 사용자가 이 점수가 실제로 "실용성이 있는지"(가장 중요하다고 한 기준) 판단해야 한다 — 판단 결과에 따라 나머지 3개 제안(고립 매치업 탐지·무게중심·폭 깊이 비교)을 계속 진행할지, 이 접근 자체를 다른 방식으로 바꿀지 정해야 한다.

### 46. 위협 가중 점수·키포인트 안내 버튼 + 키포인트 실선수 표시

- **내용**: "가중점수 옆에 버튼을 하나 만들어서 그 원리를 설명해주는 창을 하나 만들자. 키포인트 포지션에도 버튼을 만들어서 설명해주는 글을 하나 만들어서 지금 현재로는 이 선수가 있다라고 하면서 키포인트 포지션 선수도 알려주고. 근데 이렇게 설명해주는 코멘트를 만들면 전술대결을 생성할 때마다 코멘트가 작성되게 하는거지?" — 45번의 위협 가중 점수와 원래 있던 키포인트 배지(TO-DO 38 후속) 둘 다 한 줄 요약이라 "왜 이 숫자가 나왔는지"까지는 못 보여줬는데, 그걸 눌러서 보는 설명창으로 보강해달라는 요청. 마지막 문장은 "이게 DB에 저장되는 커뮤니티 댓글이냐"는 질문이었다.
- **질문에 대한 답(구현 전 먼저 확인)**: 아니다 — `comments` 테이블(TO-DO 12번, 커뮤니티 댓글)과는 완전히 무관하다. 이 설명은 렌더링할 때마다 현재 좌표·구역으로 다시 계산하는 순수 프론트엔드 값이라 아무것도 저장되지 않는다 — 국면을 바꾸거나 다른 분석을 고르면 그 즉시 다른 내용으로 바뀌고, 새로고침하면 다시 계산될 뿐 어디에도 남지 않는다. 기존 "브라질 키포인트: ..." 문구도 원래 이렇게 동작했고(TO-DO 38 후속), 이번에 추가한 설명창도 같은 성격이다.
- **구현**: 공용 `components/versus/InfoDialogButton.tsx`(신규)를 만들어 `AdvantageBadge`·`KeyZoneCallout` 둘이 공유한다 — shadcn `Dialog`(이미 `PlayerEditDialog` 등에서 쓰던 것)를 감싼 작은 ⓘ 아이콘 버튼 + 모달. `AdvantageBadge.tsx`의 위협 가중 점수 줄 옆에 붙여 "N구역 우세는 왜 동률처럼 보일 수 있는지 / 가중치는 뭘 더 크게 보는지 / 확률이 아니라는 것"을 설명한다. `KeyZoneCallout.tsx`엔 A/B 키포인트 배지마다 하나씩(총 최대 2개) 붙여 "이 구역이 왜 키포인트인지"와 "지금 이 구역에 있는 선수 목록"을 보여준다 — 선수 목록은 새 `lib/matchup.ts`의 `playersInZone(positions, players, formation, channel, third)`이 계산하는데, `computeOverload`와 똑같이 `within()`(하한 포함·상한 배제, TO-DO 45에서 export로 열어둠) 경계 판정과 골키퍼 제외를 그대로 재사용해서 여기 나열되는 인원수가 배지의 own/opp 숫자와 항상 정확히 일치하게 만들었다. A팀은 `dataA.positions`(자기 좌표 그대로), B팀은 `positionsB`(미러링된 좌표 — 키포인트 구역의 채널/서드 경계 자체가 A 프레임 기준이라 B도 A 프레임으로 옮긴 좌표를 써야 맞다)를 넘긴다. 선수 표기는 피치 마커와 같은 규칙(`positionInfoAt`의 2글자 라인 코드 + 이름, 예: "DF 다닐루 산투스")을 재사용해 화면에 이미 보이는 표기와 어긋나지 않게 했다.
- **검증**: `tsc -b`/`npm run lint`(0 errors, 기존 warning 3건만)/`npx vitest run`(188, 신규 3건 포함, 회귀 없음). 신규 유닛 테스트 — (1) 과르디올라 vs 아르테타 실제 프리셋에서 브라우저로 이미 확인해 둔 top zone(TO-DO 38-2)에 대해 `playersInZone`이 반환하는 인원 수가 해당 구역의 own/opp 숫자와 정확히 같은지, (2) 기하학적으로 골키퍼가 구역 안에 들어가는 경우에도 골키퍼가 목록에서 빠지는지. Playwright로 안첼로티 vs 이정효 수원삼성 조합을 띄워 세 버튼을 각각 눌러 스크린샷으로 확인 — 위협 가중 점수 설명창, "브라질 키포인트: 지금 이 구역에 있는 브라질 선수: DF 다닐루 산투스, DF 가브리에우 마갈량이스"(TO-DO 45에서 손으로 계산해 뒀던 leftHalf·defensive 구역의 own=2명과 정확히 일치), "수원삼성 블루윙즈 키포인트: 지금 이 구역에 있는 수원삼성 블루윙즈 선수: DF 고종현, DF 홍정호"(같은 손 계산의 center·attacking 구역 opp=2명과 일치)까지 세 모달 모두 정상 렌더링과 정확한 내용을 확인했다.
- **미확인**: 사용자가 브라우저에서 버튼 위치·모달 문구가 이해하기 쉬운지, 특히 "이게 댓글로 저장되는 거냐"는 질문에 대한 답(저장 안 됨, 매번 재계산)이 기대와 맞는지 확인해야 한다.
