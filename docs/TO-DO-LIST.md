## 항목 상세

### 66. 요청 제한·세션 보안 강화 + 신고/운영자 처리

- **배경**: 개선 로드맵 §5.5(P0). 65번 다음 우선순위를 물었을 때 "요청 제한·세션 보안 강화(신고/차단 제외)"로 좁혀서 제안했으나, 사용자가 "신고/차단도 이번에 같이"를 선택해 범위가 넓어졌다. **"차단"은 별도의 사용자 간 차단(뮤트) 기능이 아니라 운영자가 신고된 콘텐츠를 숨기거나 지우는 조치로 해석해 구현했다** — 애초 제안 문구가 "report/block + 최소한의 운영자 처리 수단"이었던 데서 이어진 해석이다. 사용자가 "이 사람 글을 안 보고 싶다"는 개인 차단(뮤트)을 의도한 거라면 다른 기능이니 알려달라 — 그건 로드맵 P2 "커뮤니티 운영과 탐색"에 더 가깝다.
- **구현**:
  - **요청 제한(`backend/ratelimit.py`, 신규)**: Redis 없이 프로세스 메모리 슬라이딩 윈도우, IP 기준(Fly-Client-IP 우선, 없으면 X-Forwarded-For의 **오른쪽 끝**만 신뢰 — 왼쪽은 클라이언트가 스푸핑 가능). 회원가입 5회/10분, 로그인 10회/5분, 댓글 작성 20회/분, 댓글 반응·좋아요·신고 각각 30회/분·30회/분·10회/시간. `reset()`을 두고 `conftest.py`의 autouse 픽스처가 매 테스트 전에 호출한다 — TestClient가 모든 요청에 같은 호스트를 쓰는 탓에 리셋 없이는 회원가입이 잦은 테스트에서 실제 로직과 무관한 429가 섞여 들어온다.
  - **세션 보안 강화(`backend/auth.py`, `models.py`)**: `Session.token` 컬럼에 원문 대신 SHA-256 해시를 저장한다(컬럼이 `NOT NULL UNIQUE`라 별도 `token_hash` 컬럼을 추가하는 대신 기존 컬럼 용도를 바꿨다 — advisor 리뷰로 발견, 처음엔 새 컬럼을 추가하려다 테스트 DB에서 즉시 insert 실패했을 문제였다). 해시 전환 이전에 발급된 세션은 자동 무효화된다(재로그인 필요, 허용 가능한 부작용). `expires_at`(30일)·`last_used_at`(5분 이상 지났을 때만 갱신 — 매 요청 쓰기 방지)을 추가했다(`_ensure_column`). 로그인 시점에 그 계정의 만료 세션을 같이 정리한다(`NULL < 만료시각`은 SQL에서 거짓 취급이라 `expires_at IS NULL`도 같이 잡아야 해시 전환 이전 세션도 정리된다).
  - **요청 크기 제한(`backend/schemas.py`, `main.py`)**: `summary` 2000자, `thumbnail` 500KB(base64 기준), `tags` 20개·항목당 30자, `annotations` 국면당 100개, `changing_points` 50개 — 필드별 Pydantic 상한. 그 앞단에 `main.py`의 미들웨어로 `Content-Length` 2MB 초과 요청은 파싱 전에 413으로 거른다.
  - **보안 헤더(`main.py`)**: `X-Content-Type-Options`·`Referrer-Policy`·`X-Frame-Options`만 추가했다. **CSP는 의도적으로 뺐다** — Google Fonts·Vite 빌드 산출물과 충돌 없이 값을 확정하려면 실제 브라우저 검증이 필요한데, 이 세션 환경은 배포된 프로덕션 사이트를 직접 눈으로 확인할 방법이 없다([[shell-sandbox-vs-real-browser-network]]) — 잘못된 CSP를 사람 확인 없이 배포하면 폰트·스크립트 로드가 조용히 깨질 위험이 있다. 미들웨어 등록 순서도 신경 썼다 — CORSMiddleware를 가장 바깥쪽(마지막 등록)에 둬야 위 413 조기 반환 응답에도 CORS 헤더가 실린다(advisor 리뷰로 발견 — 순서가 반대였다면 로컬 개발의 교차 출처 요청에서 413이 CORS 오류로 오인됐을 것).
  - **신고 + 운영자 처리(`backend/models.py`의 `Report`, `backend/routers/moderation.py` 신규)**: 분석·댓글 공통 신고 테이블(같은 사람이 같은 대상을 재신고하면 409). 운영자 판정은 DB 플래그가 아니라 `config.py`의 `admin_emails`(콤마 구분 이메일) 설정값으로 한다 — advisor 리뷰로 "가입 순서상 첫 계정" 방식을 기각했다(테스트마다 등록 순서가 달라 테스트가 우연에 좌우되고, 운영 환경에서도 user id=1이 실제로 누구인지 이 세션에서 확인할 방법이 없다). `models.User.is_admin`은 프로퍼티로 계산해 `UserOut`에 실어 보낸다(프론트가 "신고함" 메뉴 노출 여부만 판단, 실제 권한은 서버가 매 요청 재확인). "차단" 조치는 새 엔드포인트를 만들지 않고 기존 `PATCH .../visibility`·`DELETE /api/comments/{id}`에 운영자 우회 권한만 추가했다 — 같은 동작이 두 경로로 존재하는 걸 피했다.
  - **프론트(`frontend/src`)**: `ReportButton`(공용, 분석 상세·댓글 양쪽 재사용) — 클릭 시 인라인 사유 폼이 펼쳐진다(`window.prompt` 대신 기존 답글 폼과 같은 패턴). `/admin/reports`(`AdminReportsPage`) — 미해결 신고 목록 + "비공개로 전환"/"댓글 삭제"/"조치 없이 해결" 버튼. 헤더 내비에 "신고함" 링크를 운영자 계정에만 노출한다(`user.isAdmin`) — 실제 접근 제어는 서버(`auth.require_admin`)에 있고 이건 화면 정리용일 뿐이다.
  - **`ADMIN_EMAILS` 설정 완료(구현 직후 추가 조치)**: 처음엔 이 값을 설정하지 않아 아무 계정도 운영자가 아닌 상태로 커밋만 해뒀었다. 사용자에게 알리고 확인받은 뒤 로컬 `backend/.env`에 `ADMIN_EMAILS=ljh.micol@gmail.com` 추가, 배포 환경은 이메일이 담기는 값이라 `fly.toml`의 `[env]`(평문, git 커밋됨)가 아니라 `flyctl secrets set ADMIN_EMAILS=...`로 설정했다(머신 재기동 발생 — 사용자 승인 하에 실행).
- **검증**: `./.venv/Scripts/python.exe -m pytest -v` → 45개 전부 통과(신규 14개 — 세션 해시/만료·요청 제한·요청 크기 제한·신고 플로우·운영자 우회), 연속 2회 실행으로 요청 제한 테스트 간 상태 누수가 없는지 확인. 프론트 `tsc -b`(0 errors) / `npm run lint`(0 errors, 기존 경고 3개만) / `npx vitest run`(209개 전부 통과) / `npm run build` 성공. 배포 후 `curl https://tacticraft.fly.dev/openapi.json`으로 `/api/moderation/reports`·`/api/analyses/{id}/report`·`/api/comments/{id}/report` 경로가 실제로 떠 있음을 직접 확인했다(첫 배포 시도는 백그라운드 실행을 이중으로 감싸 로그가 끊겨 재배포로 확정 — 두 번째 배포에서 같은 이미지 다이제스트가 캐시로 재사용된 것을 보아 첫 배포도 실제로는 끝까지 됐던 것으로 보이지만, 확인 없이 넘어가지 않고 재배포·재검증했다). **미확인**: 관리자 UI(`/admin/reports`, "신고함" 메뉴)는 실제 브라우저로 눈으로 본 적 없다 — 셸에서 띄운 로컬 서버가 이 세션의 실제 브라우저와 네트워크가 분리돼 있어서다([[shell-sandbox-vs-real-browser-network]]). 사용자가 `ljh.micol@gmail.com`으로 로그인해 직접 확인해야 한다.

### 67. Fly.io 콜드 스타트 대응

- **배경**: 개선 로드맵 §5.6(P0 마지막 항목). `min_machines_running = 0`(TO-DO 59) 설정과 프론트의 헬스체크가 충돌하는 문제 — 트래픽이 없으면 Fly 머신이 꺼지고, 다음 요청이 오면 Fly 프록시가 연결을 물고 있다가 머신이 뜨면 응답한다. 이 콜드 스타트 동안 프론트의 헬스체크(`fetchHealth`, 2초 타임아웃)가 먼저 실패하면 저장 버튼이 "서버 미기동"으로 비활성화됐는데, 정작 그 2초는 콜드 스타트가 끝나기엔 너무 짧아 매번 실패했다 — 실제로는 곧 뜰 서버인데도 사용자가 저장을 시도할 방법 자체가 없었다.
- **구현**:
  - **헬스체크 타임아웃 확대 + 제한된 백오프 재시도(`frontend/src/lib/api.ts`의 `fetchHealth`, `frontend/src/hooks/useServerHealth.ts`)**: 타임아웃 2초→8초, react-query `retry: 2`·`retryDelay` 지수 백오프(1.5초→3초, 6초 상한) — 최대 3회 시도. `useServerHealth` 하나를 고치면 이를 쓰는 `SaveButton`·`DuplicateButton`·`RecentAnalyses`·`AnalysesPage`·`CommunityPage`·`VersusPage` 전부 같이 좋아진다. **의도적으로 안 한 것**: 실패 상태에서 주기적으로 자동 재확인(`refetchInterval`)하는 안을 처음엔 넣었다가 advisor 리뷰로 뺐다 — "백엔드가 꺼져 있어도 편집·PNG 내보내기는 동작해야 합니다"가 이 프로젝트의 정식 지원 개발 흐름인데, 그 상태로 화면을 켜 두면 영원히 실패하는 요청을 계속 폴링하게 되는 부작용이 있었다.
  - **저장 버튼이 헬스체크 실패만으로 영구 비활성화되지 않게(`frontend/src/components/editor/SaveButton.tsx`)**: `disabled`에서 `!isServerUp`·`isChecking`을 뺐다 — 이제 비로그인·저장 진행 중일 때만 비활성화된다. 클릭하면 실제 저장 요청이 그대로 나가 Fly 프록시를 거치며 서버를 깨운다. `saveState`(`idle`/`waking`/`saving`/`retrying`/`done`)로 "서버 깨우는 중… → 재시도 중… → 저장 완료" 진행 상태를 보여준다. 저장 요청 자체도 최대 2회 재시도한다 — 단, ApiError(서버가 실제로 응답을 준 4xx/5xx)는 재시도하지 않고 바로 실패로 확정한다(재시도해도 같은 결과라서). ApiError가 아닌 실패(네트워크 단절 등)만 재시도하는데, `apiFetch`가 애초에 클라이언트 타임아웃을 걸지 않는다는 전제(즉 "응답을 못 받았다 = 요청이 서버에 닿지도 못했을 가능성이 높다") 위에 서 있는 안전장치라 코드에 명시해 뒀다 — 나중에 `apiFetch`에 타임아웃이 추가되면 이 가정이 깨지므로 재검토가 필요하다.
  - **`useCurrentUser`도 같은 문제가 있어 같이 고쳤다(`frontend/src/hooks/useAuth.ts`, advisor 리뷰로 발견)**: `/api/auth/me`가 콜드 스타트 중 일시적으로 실패하면 `isLoggedIn`이 false로 굳어버려, 실제로는 로그인 상태인데도 `SaveButton`이 "로그인이 필요합니다"로 막혀버렸다 — 헬스체크 우회는 고쳤지만 인증 체크가 같은 자리에서 다시 막는 셈이라 §5.6의 목표를 달성하지 못했을 문제였다. 401(정상적인 비로그인 상태 — 절대다수의 익명 방문이 여기 해당해 재시도하면 전원이 지연을 겪는다)은 재시도하지 않고, 그 외 실패만 헬스체크와 같은 백오프로 재시도하도록 고쳤다.
- **검증**: 프론트 `tsc -b`(0 errors) / `npm run lint`(0 errors, 기존 경고 3개만) / `npx vitest run`(209개 전부 통과) / `npm run build` 성공. **미확인 — 실제 콜드 스타트 시나리오는 사람이 확인해야 한다**: `min_machines_running = 0`이라 트래픽 없이 몇 분 두면 머신이 자동으로 꺼진다 — 그 상태에서 https://tacticraft.fly.dev 를 새로 열고 편집 후 저장을 눌러, 버튼이 비활성화되지 않고 "서버 깨우는 중… → 저장 완료" 순서로 넘어가는지 확인해달라. 이 세션은 셸에서 띄운 로컬 서버가 실제 브라우저와 네트워크가 분리돼 있어([[shell-sandbox-vs-real-browser-network]]) 이 흐름을 직접 눈으로 본 적 없다.

### 71. 모바일 핵심 여정 개선

- **배경**: 개선 로드맵 §6.2(P1 §6 "일상 사용성 개선" 세 번째 항목). 로드맵이 6개 항목을 지목했는데, 구현 전에 실제 코드로 하나씩 확인해보니 이미 된 것과 안 된 것이 섞여 있었다.

  - **이미 되어 있던 것(확인만)**: "저장 버튼과 썸네일 캡처 상태를 하나의 command/state로 통합한다" — `SaveButton.tsx`의 `handleSave`가 이미 썸네일 캡처와 저장을 한 함수 안에서 처리하고, 하나의 `saveState`(idle/waking/saving/retrying/done, TO-DO 67·68에서 만듦)로 버튼 라벨을 몰아서 관리하고 있었다. 추가 작업 없이 "이미 만족됨"으로 처리.
  - **범위 밖으로 둔 것**: "생성→편집→로그인→저장→공유 모바일 E2E 테스트 추가" — 이 저장소엔 Playwright 같은 E2E 테스트 인프라 자체가 없다(vitest 단위 테스트뿐). 새로 들이는 건 CI 연동 여부까지 같이 걸리는 별도 인프라 결정이라(TO-DO 65가 이미 "CI 연동은 아직 없음"으로 남겨둔 공백과 같은 사안), 이번 스코프에 묶지 않고 따로 논의할 항목으로 남긴다.

  - **근본 원인 2(확정, 실기기 진단으로 수치 확보)** — `compositeCanvas`에 0×0 rect를 조용히 건너뛰지 않고 에러로 노출하는 진단을 추가하자, 사용자 실기기에서 정확한 값이 나왔다: `svg#0 rect가 0.0x423.0` — **width만 정확히 0, height는 정상**. 원인은 `ShareCard`/`VersusShareCard`/`SharePngCard` 세 곳 모두 `<Pitch>`를 감싼 안쪽 div가 `height:'100%'`만 있고 width가 없었던 것 — row-flex 안의 아이템이라 width가 "내용 기준 shrink-to-fit"으로 계산되는데, 내용인 Pitch의 wrapper가 또 `w-full`(부모의 100%)이라 서로가 서로의 크기를 기준 삼는 순환 참조가 됐다. 화면에 그려질 때는 대부분 브라우저가 (w-full의 100%가 미확정 부모 기준으로는 안 풀려 사실상 auto로 취급되고, 그 결과 Pitch 자신의 `aspect-[68/105]`가 대신 개입하는) 우연한 경로로 무난하게 보였지만, 이 카드들은 전부 `position:absolute;left:-9999px`로 화면 밖에 렌더링되는데 이 상태에서 iOS WebKit이 순환을 0으로 풀어버렸다. 1차로 `width:100%`를 강제해 검은 화면은 고쳤지만, 그러면 Pitch 자신의 `h-full`+`w-full`이 둘 다 "정해진 값"이 되며 `aspect-ratio`가 완전히 무시돼 피치가 컨테이너 박스 그대로 찌부러지는 회귀가 생겼다(사용자 확인: "세로로 되게 찌부돼서 보여") — `width:100%` 대신 wrapper 자체에 `aspectRatio`(portrait `68/105`, landscape `105/68`)를 직접 지정하고 `width:'auto'`, `flex:'none'`으로 고쳐 순환도 끊고 비율도 지켰다. Chromium에서 `getBoundingClientRect()`로 직접 재본 비율(0.6478)이 기대값(0.6476)과 일치하는 것까지 확인(순수 레이아웃 읽기라 자동화 탭 한계와 무관).
  - **근본 원인 3(확정) — html-to-image의 foreignObject 리소스 제약, 그리고 "텍스트 전용 클론"의 새로운 결함**: 피치가 보이자 이번엔 "피치만 보이고 카드 텍스트가 안 보임"으로 반전 — 원인을 좁히던 중 애초에 피치(살아있는 svg든 미리 래스터화한 img든)를 html-to-image에 통째로 넘기면 선수 마커까지 포함해 그 서브트리 전체가 항상 비었던 것으로 재확인(사용자가 "선수 마커도 전혀 안 보임"까지 확인) — "이미지로 쓰이는 SVG는 foreignObject 안에서 추가 리소스를 로드할 수 없다"는 스펙 제약으로 추정하고, 카드를 복제해 피치 자리를 빈 자리표시자로 바꾼 "텍스트 전용" 클론만 html-to-image로 캡처하고 피치는 `rasterizeSvg`(순수 svg→canvas, foreignObject를 거치지 않음)로 따로 래스터화해 `ctx.drawImage`로 직접 합성하는 방식(`compositeCanvas`)으로 재작성. 그런데 이 "텍스트 전용" 캡처가 실기기에서 매번 완전히 빈 캔버스를 냈다 — 캔버스 크기 검증(정상, 2160x2160)과 제목 영역 불투명 픽셀 수 진단(0개)을 추가해 확정. "텍스트 캡처는 항상 됐다"는 이전 가정은 `toBlob(node)`를 라이브 노드에 직접 호출하던 시절의 증거였지, `toCanvas(clone)`을 방금 만든 detached 복제본에 호출하는 경로는 실기기로 검증된 적이 없었다(advisor 리뷰로 확인). Chromium에서 `prepareTextOnlyClone`을 손으로 재현해 클론의 레이아웃 수치(카드 1080x1080, 텍스트 div 전부 정상 크기·좌표)는 완전히 정상임을 확인해 레이아웃 문제가 아님을 배제했다.
  - **최종 수정 — 복제본을 아예 쓰지 않는다**: 라이브 카드 노드 안의 피치 svg를 그 자리에서 잠깐 빈 자리표시자로 바꿔치기하고, 텍스트 캡처가 한 번도 실패한 적 없는 경로(라이브 노드에 직접 `toCanvas` 호출)로 캡처한 다음, `finally`에서 반드시 원래 svg로 되돌린다(`withPitchesSwappedOut`) — React가 이 서브트리를 소유하므로, 복구 시점에 자리표시자가 이미 DOM에서 사라졌으면(다른 상태 변화로 리렌더링) 저장해둔 부모·다음형제 정보로 직접 다시 끼워 넣도록 방어했다. `captureThumbnail`에도 `waitForMorphing`을 추가(원래 없었음) — 저장 시점은 다른 상태 변화가 겹칠 수 있어 교체 창이 더 위험해질 수 있다. Chromium에서 스왑/복구 메커니즘 자체(라이브 svg가 같은 인스턴스로 같은 자리에 정확히 복구되는지)를 순수 DOM 조작으로 검증한 뒤 배포. **사용자 실기기 최종 확인(2026-09-21): "다 보여 됐어"** — 텍스트와 피치가 함께 정상적으로 캡처됨을 확인.

  - **후속 버그(2026-09-21) — "핸드폰에서는 코멘트가 끝까지 다 보이는데 컴퓨터에서는 짤려"**: 위 PNG 내보내기 파이프라인 재작성이 끝난 직후 새로 들어온 리포트. 두 가지가 겹쳐 있었다.
    1. `ShareCard.tsx`의 `useFitFontSize`(코멘트를 `boxHeight`에 맞게 폰트 크기를 줄이는 훅)가 컴포넌트 마운트 시점(웹폰트 "IBM Plex Sans KR" 다운로드가 아직 안 끝났을 수 있는 시점)에 `el.scrollHeight`를 딱 한 번만 재고, 이후 실제 웹폰트가 로드돼도 재계산 트리거가 없었다 — 측정에 쓰인 그 순간의 폴백 폰트가 OS마다 달라 계산된 폰트 크기가 어긋났다. `document.fonts.ready`가 끝난 뒤 한 번 더(항상 `maxSize`부터 다시) 재계산하도록 고쳤다.
    2. 그래도 사용자가 "아직 좀 잘려"로 재확인 — 남은 원인은 `exportImage.ts`의 `compositeCanvas`가 `toCanvas` 호출에 `skipFonts: true`를 쓰고 있던 것. html-to-image가 카드를 `foreignObject` SVG로 직렬화해 별도 이미지 리소스로 렌더링할 때, 그 렌더링 컨텍스트는 문서에 등록된 `@font-face`를 상속받지 못한다 — `skipFonts`로 임베딩 단계 자체를 건너뛰므로 캡처된 PNG는 **항상 OS 기본 폰트로 대체 렌더링**되고 있었다(화면 측정은 실제 웹폰트 기준인데 캡처는 OS 폴백 기준이라 폭이 달랐던 것 — 1번 수정만으로는 이 간극을 못 없앴다). `skipFonts`가 원래 있던 이유는 Google Fonts CSS `<link>`에 `crossorigin`이 없어 `cssRules`를 못 읽어 CORS `SecurityError`가 났기 때문(2026-09-11, GIF 39프레임에서 프레임마다 반복돼 70초 넘게 걸렸던 문제) — `curl`로 Google Fonts `css2` 엔드포인트가 `Access-Control-Allow-Origin: *`를 보내는 걸 확인하고, `index.html`의 폰트 `<link>`에 `crossorigin="anonymous"`를 추가해 `exportImage.ts`(단발성 PNG 캡처, `exportCard`·`captureThumbnail`가 공유하는 `compositeCanvas`)에서만 `skipFonts`를 제거했다 — `GifExportRunner.tsx`는 39프레임 반복 구조라 임베딩 비용을 감당하기 어려워 `skipFonts: true`를 그대로 남겼다(GIF는 PNG와 다른 폰트로 렌더링되는 별도 불일치가 남아 있으나 이번 스코프 밖). 폰트 파일을 새로 fetch+embed하는 비용을 감안해 `toCanvas`의 타임아웃도 20s→25s로 늘렸다. claude-in-chrome으로 `toBlob`을 가로채 캡처된 캔버스를 화면에 미리보기로 띄우는 방식으로 자체 검증(표시용 긴 코멘트 텍스트가 끝까지 보임을 확인) 후 배포, **사용자 최종 확인: "좋아. 이제 안 잘린다"**.
